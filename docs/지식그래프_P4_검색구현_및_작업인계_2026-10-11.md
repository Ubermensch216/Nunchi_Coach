# 지식그래프 P4 검색 구현 및 작업 인계

2026-10-11. 다른 PC의 최신 커밋 `4d32a04`를 확인하고 [P3 갱신·재개](지식그래프_P3_구현기록_2026-10-11.md) 다음 P4를 재개했다. `git fetch origin` 후 기존 HEAD와 origin/main 차이는 0이다. 이번 변경은 아직 커밋·푸시하지 않았다.

## 구현한 동작

- `search/query.py`: 기존 `years`는 문서연도(`eff_year`)로 유지한다. `year_basis`에 performance/evaluation/submitted/case를 추가했다. 업무연도는 `doc_years`의 해당 kind만 사용하며, case는 선택 수행 건의 `period_year`와 명시적 `basis_doc_id`를 사용한다. 문서 선택과 업무 제한은 교집합이다. 근거 없는 연도를 보충하지 않는다.
- 벡터·FTS·직접 필드·최종 문맥 선택이 같은 SQL 범위 조건을 사용한다. 선택 사본을 전역 대표본으로 바꾸지 않는 기존 동작을 유지했다. 노트북 worker가 명시적 범위를 전달하며, 실제 선택 자료와 교집합을 적용한다.
- `search/graph.py`: 깊이 1, seed 8, 방문 support 최대 100, 원문 후보 5, 기본 시간 예산 150ms. SQL LIMIT과 SQLite progress handler로 조회를 제한한다. 본문 대조까지 포함하며 시간 초과 결과는 전부 버린다. 이 예산은 대규모 성능 보장이 아니다.
- 현재 게시 세대의 활성 quote support만 검색한다. 원본 해시·파싱 fingerprint·위치·인용·현재 chunk 연결을 재검사한다. source record만 있는 관계와 inferred 관계는 답변 후보로 승격하지 않는다. 거절·무효 근거는 제외한다.
- 별칭은 같은 관계의 활성 support에 연결된 provenance를 요구한다. 동명 UUID를 합치지 않는다. 반환값에는 전역 이름이나 설명 대신 claim/evidence/generation/검증 버전/범위 fingerprint와 관계 경로를 담는다. 사람의 전역 별칭과 명시적 동일성 판정의 검색 확장은 아직 연결하지 않았다.
- 일반 RAG에서는 기존 질의·변형 질의 검색 뒤 그래프 순위를 별도 가중 RRF(0.2)로 더한다. 검증한 그래프 후보만 strong 후보에 추가하며 기존 TOP_K·문서별 상한·재정렬·문장 검증을 유지한다. 모델 OFF 검색도 같은 연결을 사용한다. 직접 필드 답변은 기존 전체 허용 원문 대조 결과를 유지하고 그래프 진단만 추가한다.
- `knowledge_search_mode` 메타 설정은 기본 off다. shadow는 후보·시간·fallback을 기록하고 기존 순위·근거를 유지한다. on은 내부 시험용이며 사용자 설정 화면의 활성화는 추가하지 않았다.
- 답변 반환 전에 content/index/kg revision과 호출자의 범위 fingerprint를 비교한다. index rollback도 값의 동일성으로 감지한다. 노트북은 법령 조회 이후 저장 트랜잭션에서 writer를 확보하고 revision과 자료 선택을 다시 확인한다. 그래프 경로가 있는 노트북 인용은 경로·세대·검증 버전을 함께 저장한다. overview와 법령 조회의 기존 생성 경로는 유지한다.
- 기존 DB를 수정·이행하지 않는 읽기 전용 진단 명령과 `Database(readonly=True)`를 추가했다.

## 내부 실행 방법

```powershell
.\.venv\Scripts\python.exe -m app.tools.knowledge_search --project D:\경로\기존프로젝트 --query "신청서" --docs 1 2
.\.venv\Scripts\python.exe -m app.tools.knowledge_search --project D:\경로\기존프로젝트 --query "2025년 실적" --year-basis performance
.\.venv\Scripts\python.exe -m app.tools.knowledge_eval --graph shadow --json .test_runs/knowledge-p4-shadow.json
.\.venv\Scripts\python.exe -m app.tools.knowledge_eval --graph on --json .test_runs/knowledge-p4-structure.json
```

`--docs` 생략은 전체 범위, 숫자 없이 `--docs`만 쓰면 빈 선택이다. case 범위는 `--year-basis case --case ID`를 함께 사용한다. 진단 명령은 사용자 프로젝트의 검색 모드를 변경하지 않는다.

## 비교 결과와 한계

동결 합성 120문항에서 shadow와 구조 그래프 B 모두 범위 밖 노출 0건, 기존 FTS 대비 검색 결과 변화 0건이다. 단순·시점 질문 Recall@10 1.0, 별칭 0.6, 연결 0.5로 기준선과 같다. 게시된 구조 주장 51개는 대부분 문서 배정 관계이고, 서술형 문서에서 검색 자격을 갖춘 관계 인용을 생성하지 못해 120문항 모두 `no_scoped_seeds`로 기존 검색을 사용했다.

평가용 그래프는 입력 문서와 업무 배정에서 제품의 기존 규칙 추출기로 생성했다. 정답 인용과 expected 관계를 구축에 넣지 않았다. 모델 OFF FTS 비교이며 벡터 RAG·LLM 답변·실제 자료 품질·대규모 RSS 측정이 아니다.

따라서 **P4의 범위·검색 기반은 구현했으나, 품질 게이트를 충족해 P4 전체를 완료하거나 기본 활성화한 상태는 아니다.** 다음 작업은 구조 추출기가 놓치는 서술형 관계와 별칭·동일성 해소를 검토하고, 원문 근거를 유지하는 확장으로 연결 질문 개선을 측정하는 것이다. 이후 연도 기준 UI, 그래프 충돌·대체 진단, 벡터/모델 A/B, 1,000문서 성능 평가가 남아 있다. 모델 관계 후보는 원래 계획의 P8 범위이며 이번에 추가하지 않았다.

## 검증

새 시험은 범위 밖 seed·동명 자료 분리·거절·hash 변경·chunk 변조·시간 초과 fallback·shadow 동일성·별도 RRF·연도 종류·Case 교집합·저장 경로·index rollback·범위 변경·법령 조회 뒤 저장 경쟁·읽기 전용 접근·고차수 탐색 제한을 확인한다.

최종 관련 회귀 **298건 통과(120.28초)**. knowledge search/eval/projection/lifecycle/schema, query_scope, rag/hybrid/filters/scope_upgrade/facts, notebook chat/notebooks/UI, reindex, job_lifecycle, migrations를 함께 실행했다. 결과는 `.test_runs/knowledge-p4-final.xml`과 `.test_runs/knowledge-p4-final.txt`다. 전체 저장소 회귀 결과와 합산하지 않는다.

고차수 제한 시험은 처음에 별칭 seed 8개만 선택해 방문 수 8을 측정하는 잘못된 조건으로 실패했다. 공유 업무 개체를 검색 순위 seed로 지정해 고차수 경로를 실제 방문하도록 시험을 수정했고, 최종 위 실행에 포함해 통과했다. 제품의 방문 한도를 변경하지 않았다.

최종 코드 Windows PyInstaller 빌드와 EXE `selftest tests/fixtures/sample_tree` 모두 통과했다. 실행물은 `.test_runs/bundle-knowledge-p4/NunchiCoach/`에 있으며, 기본 `dist` 배포본을 덮어쓰지 않았다. 자체 점검에서 선택 원문의 그래프 근거 검색·빈 선택 제외와 기존 복원→수행 기록→갱신→인계 왕복을 확인했다. 개발 소스 자체 점검 및 `git diff --check`도 통과했다.

실자료 품질, 사람이 직접 사용하는 화면 시험, 실제 한글 실행 검증은 포함하지 않는다. 기존 `.analysis_audit/` 추적에 따른 저장소 guard 문제는 이번 작업에서 정리하지 않았다.
