작성일 2026-10-15 · 앞 단계 [P2 구현 기록](규제개혁_비교연구_P2_구현기록_2026-10-14.md) · 근거: P1-1·P1-2·P1-3 기록의 '남은 것'

P0~P2를 마친 뒤 남은 기능 세 가지를 했다.

## 1. 건 확인·고치기 화면 (P1-1 남은 일)

| 항목 | 내용 | 위치 |
|---|---|---|
| 들어가는 곳 | 업무 매뉴얼 '건별 현황' 구획의 **건 확인·고치기**. 건이 있거나, 우리 기관을 몰라 건 목록을 읽지 못한 업무에만 보인다 | `ui/views/work_workspace.py` |
| 건마다 | "자료: (자료로 확인한 진행)"과 공문 자취(2장)를 먼저 보이고, 그 아래 **담당자 확인**(정하지 않음/제출 확인/수용 확인/부분 수용 확인/불수용 확인/개선 시행 확인/종결), 메모(공문 번호, 확인한 곳), 근거, **건이 아님** | `ui/views/matter_dialog.py`(신규) |
| 지키는 것 | 자료가 말한 진행과 사람이 정한 진행을 나란히 둔다(덮지 않는다). 정한 것·메모·뺀 것은 다시 분석해도 남는다. 뺀 건은 아래에 모아 **되돌리기**. 실행 승인이 아니라 이 앱 안의 확인 기록이다 | `matters.review`(빈 값 = 정한 진행 지우기) |
| 우리 기관 | "우리 기관: 가나구(파일 이름에서 추정 / 담당자가 정함)"과 **바꾸기**. 정하지 못했으면 매뉴얼이 "우리 기관을 정하지 못해 표 계산 문서 N건의 건 목록을 읽지 않았습니다"라고 말하고, 화면에서 정하면 건 목록과 공문 자취를 다시 읽는다 | `matters.own_locality_basis`, `waiting_for_locality` |

## 2. 공문으로 건의 진행 잇기 (P1-1·P1-3 남은 일)

실자료에서 건 제목은 목록 밖의 문서에 이렇게 나온다.

- 부처 검토결과 **회신 공문**(받은 공문, 시행 번호·접수 번호가 있음)과 같은 폴더의 붙임: "□ 안 건 명 : 90. (건 제목)" … "□ 검토의견 : □수용 □일부수용 □기시행 □중장기검토 ■수용곤란".
- 규제개혁위원회 심의결과 알림·심의의결서: 표의 한 행 (건 제목) | 개정.
- 구의회 의결 의안 알림: (조례안 이름) | 원안가결.
- 자치법규 정비 추진 결과 보고: (건 제목) | 개정.
- 계획·실적·평가 증빙: 제목만 나온다.

| 항목 | 규칙 | 위치 |
|---|---|---|
| 찾기 | 건 제목(띄어쓰기·기호를 뺀 꼴, 8자 이상)이 나온 문서. 표 계산 문서(목록 — 건 구조가 읽음), 압축 문서 자신(파일 목록), AI 생성·발간물은 보지 않는다 | `core/matter_trail.py`(신규) |
| 결과 읽기 | 제목이 나온 조각부터 **다음 건 머리('□ 안 건 명', 행 번호 칸, 다른 건 제목) 전까지** 8조각 안에서만: 칸에 표시한 낱말(■·☑·▣·√…), '검토의견: …' 같은 이름표 값, 짧은 결과 칸(개정·존치·폐지·원안가결·부결…). 다른 건의 표시를 가져오지 않는다 | `read_window` |
| 덮개 공문 | 그 문서가 공문이면 그 공문, 아니면 같은 폴더(같은 압축)의 공문 가운데 이름이 가장 많이 겹치는 것. 시행 번호와 날짜, 받은/보낸/내부 공문 | `letter_of`, `_cover` |
| 갈래 | 회신(검토의견) · 심의·의결 결과 · 의회 의결 · 추진 결과 보고 · 보낸 제출 공문 · 언급 | `_signal` |
| 진행 | 목록에 있음 → 제출 공문 있음 → 취합 목록에 있음 → 회신 있음 → **심의·의결 결과 있음**. 목록의 회신 칸이 있으면 그 글로 갈래를 정하고, 없으면 붙임의 표시로 정한다("검토결과 문서의 표시로 판단"). **의회 의결·결과 보고의 '개정'은 진행으로 올리지 않는다** — "시행 근거 후보 … 시행됐는지 담당자가 확인" | `matters.settle`, `progress_line` |
| 다음 행동 | 시행 근거 후보가 있는데 담당자가 '개선 시행 확인'·'종결'을 정하지 않은 건: "[건별 진행 확인] 개정·의결 자료가 있는 건 N건 … 공포·시행일, 시스템 반영을 확인해 '건 확인·고치기'에서 '개선 시행 확인'으로 적으세요". 회신이나 심의 결과가 이어진 건은 '회신이 없다'고 묻지 않는다 | `continuity.next_actions`, `matters.to_confirm` |
| 근거 | 건의 근거에 목록의 행과 함께 진행을 말한 공문·붙임의 자리를 넣는다. 제목만 나온 문서는 근거로 늘어놓지 않고 건 확인 화면에 "제목만 나온 문서 N곳"으로 센다(건마다 30곳까지 저장) | `matters.for_task`, `matter_mentions` |
| 저장 | `matter_mentions`(건·문서·위치·갈래·결과·회신 갈래·덮개 공문·인용·문서 판). 업무 복원 때마다 건 목록 다음에 다시 세운다. 분석 알림에 "공문·붙임에서 찾은 회신·심의 결과 N" | `db/matter_schema.sql`, `reconstruction.restore` |

## 3. 압축 안의 문서를 따로 문서로 (P1-2 남은 일)

| 항목 | 내용 | 위치 |
|---|---|---|
| 문서 행 | 구성원마다 문서 행을 만든다: 경로 `압축 경로\압축 안 경로`, `parent_id`(압축 문서), `member`(압축 안 경로), 구성원 자신의 해시·크기·수정 시각(압축 안의 원래 시각)·파서·본문·검색 색인. 압축 문서 자신에게는 파일 목록만 남긴다(같은 본문이 두 번 검색되지 않게). 압축 속 압축의 구성원도 같다. 읽을 수 있는 형식의 구성원만 싣고(보호·스캔처럼 못 읽은 것도 상태와 함께 싣는다), 실행 파일·한도 초과·풀린 폴더에 같은 파일이 있는 구성원은 싣지 않는다 | `ingest/members.py`(신규), `parsers/archive.py`(`Member`), `ParseResult.members`, `jobs/pipeline._parse` |
| 디스크에 없다 | 자료원 훑기는 구성원을 보지 않는다(부모를 따른다). 압축이 사라지면 구성원도 '원본 없음', 돌아오면 함께 돌아온다. 다시 읽기는 압축을 다시 읽어서 한다 — 구성원의 파서 판이 바뀌거나 실패 재시도·기록 복구가 구성원을 가리키면 그 압축을 다시 읽게 한다. 그림·스캔 읽기 단계는 구성원을 고르지 않는다 | `repo.paths_for_source`·`mark_missing`·`mark_seen`·`repair_interrupted`, `pipeline.retry_failures`, `members.refresh_outdated`, `pictures.candidates` |
| 다시 읽을 때 | 해시와 읽은 판이 같은 구성원은 손대지 않는다(시점·갈래·업무·사람의 교정 유지). 바뀐 구성원은 분석 결과를 버리고 다시 싣고, 압축에서 빠진 구성원은 지우지 않고 '원본 없음'으로 둔다 | `members.explode` |
| 업무 | 업무 찾기(폴더·본문 묶기)에 끼지 않는다 — 압축 이름이 업무 폴더로 잡히지 않게. 문서 갈래 확인 단계 앞에서 부모 압축이 붙은 업무에 함께 붙이고(근거 "압축파일 안의 문서: 이름"), 부모가 옮기면 따라 옮긴다. 사람이 직접 업무를 정했거나 업무에서 뺀 구성원은 건드리지 않는다 | `members.inherit_tasks`, `discover._protected_documents`, `pipeline._roles` |
| 갈래·시점·값 | 구성원은 보통 문서처럼 자기 본문으로 갈래·해·시점을 정하고, 업무 값·건 목록·공문 자취의 근거가 된다. 압축 문서 자신(파일 목록)은 여전히 업무 값의 근거가 아니다 | — |
| 건 목록 | 압축 안의 표 계산 문서도 건 목록으로 읽는다. 압축 원본의 해시가 분석한 판과 같고 꺼낸 구성원의 해시가 기록과 같을 때만, 격리된 임시 폴더에 순번 이름으로 꺼내 읽고 지운다 | `matters.rebuild`, `members.extracted` |
| 열기 | 원본 열기는 압축에서 꺼낸 **읽기 전용 사본**(앱의 임시 폴더, 원래 파일 이름)을 연다. 압축이 분석 뒤에 바뀌었으면 열지 않고 까닭을 말한다. 문서 목록의 '폴더 열기'는 그 압축 파일을 가리킨다. 규칙 답변(사실 조회)은 압축이 분석한 판 그대로일 때만 구성원을 쓴다 | `ui/widgets/common.open_original`, `ui/views/documents.py`, `search/facts.py` |
| 판 | 압축 파서 판 `archive:3` — 기존 압축은 다음 분석에서 한 번 다시 읽혀 구성원이 문서로 실린다. 준비 상태의 본문 추출 층에 "(압축파일 안의 문서 N건 포함)" | `parsers/base.py`, `initial_analysis.layers` |

## 5. 시험

- `tests/test_matter_review.py` 5건: 기관을 몰라 목록을 읽지 않았다고 말함, 화면에서 기관을 정하면 목록을 읽음, 정한 진행·메모가 재분석 뒤에도 남고 진행 확인 안내에서 빠짐·지우면 자료대로, 건이 아님·되돌리기, 매뉴얼 버튼은 건이 있는 업무에만.
- `tests/test_matter_trail.py` 7건: 회신 붙임의 체크 표시가 회신 갈래가 되고 덮개 공문을 말함, 다음 건 머리 뒤의 표시를 가져오지 않음, 목록의 회신 칸이 붙임보다 먼저, 의회 의결은 시행 근거 후보이고 '개선 시행 확인' 뒤에는 묻지 않음, 위원회 표의 심의 결과, 제목만 나온 계획은 진행을 바꾸지 않고 근거로 늘어놓지 않음, AI 생성 문서는 자취가 아님, 매뉴얼에 공문이 보임.
- `tests/test_archive_members.py` 6건: 실제 분석 실행 위에서 구성원이 자기 해시·본문·색인·시점을 가진 문서가 되고 원본 폴더는 그대로, 재분석이 구성원과 사람의 교정을 지키고 바뀐 압축은 바뀐 구성원만 갈고 빠진 구성원은 '원본 없음', 압축이 사라졌다 돌아오면 구성원도 함께, 업무 물려받기와 사람 결정 존중, 압축 안의 건 목록, 읽기 전용 열람 사본과 바뀐 압축 거부.

## 6. 남은 것

| 항목 | 비고 |
|---|---|
| 한글·PDF 표의 건 | 위원회 안건·건의서 본문을 건으로 세우는 것은 아직 하지 않았다. 공문 자취는 목록에서 세운 건의 제목으로만 찾는다 |
| 보낸 제출 공문 | 실자료에는 우리 기관이 상급기관에 보낸 제출 공문이 없다(제출은 붙임 파일만 남았다). 규칙은 넣었으나 실자료로 확인하지 못했다 |
| 구성원을 다른 업무로 | 구성원의 업무는 부모를 따른다. 다른 업무로 옮기려면 문서 화면에서 사람이 옮긴다 |
