# 노트북 열기 시 기존 자료 재처리 방지

2026-10-10. 노트북을 열 때 기존 업로드 문서가 다시 처리되는 동작을 수정했다.

## 원인

`SourcesPanel.set_notebook()`이 화면을 열거나 편집 가능 상태로 전환할 때
`_resume_uploads()`를 자동 호출했다. 이 함수는 중단된 업로드뿐 아니라 현재 파서와
버전이 다른 성공/부분 추출 문서도 선택했다. 최근 PDF·Excel·HWP/HWPX 파서 버전 변경 후에는
이미 준비된 자료가 열기 동작으로 재파싱·색인·요약될 수 있었다.
진행/완료 문구도 ‘올린 파일’·‘추가했습니다’여서 기존 자료의 업데이트를 새 업로드처럼 표시했다.

## 변경

- 노트북 열기·새로고침은 저장된 결과를 표시한다. 업로드 처리 워커를 자동 시작하지 않는다.
- 중단된 자료가 있으면 **자료 처리 이어서**, 파서 업데이트 대상만 있으면 **자료 업데이트**
  버튼에 건수를 표시한다. 사용자가 버튼을 눌러 실행한다. 보관한 노트북에는 표시하지 않는다.
- 처리 대상을 현재 노트북의 이용 가능한 업로드 자료로 제한한다. 다른 노트북의 대기 자료를
  함께 처리하지 않는다.
- 워커의 대기열에 문서가 남았더라도 현재 파서로 본문/섹션을 이미 저장했다면 `reused`로
  반환한다. 중복 파싱·날짜 처리·임베딩 준비·요약을 다시 호출하지 않는다.
- 실제 워커가 시작되지 않은 대기 자료는 ‘처리 대기’로 표시한다. 기존 자료 처리의 완료는
  ‘처리했습니다’, 저장 결과 재사용은 ‘기존 분석 결과를 사용했습니다’로 표시한다.
- 새 파일 올리기, 명시적 업데이트 및 중단 후 재개 경로는 유지한다. 현재 파서와 다른 결과도
  노트북 열기만으로 무효화하지 않는다. 기존 본문·요약·대화와 근거는 유지한다.

## 검증

현재 파서 문서, 오래된 파서 문서, 처리 대기 문서 각각에 대해 세 번 열기/닫기/새로고침을
실행했다. 워커 시작 0회, 문서·본문·요약 불변을 확인했다. 명시적 재개가 현재 노트북만
선택하는지, 보관 노트북에서 실행되지 않는지, 같은 문서를 두 번 업데이트하면 한 번만
파싱하는지, 완료된 대기열 문서가 요약 모델을 다시 호출하지 않는지도 검증했다.

초기 관련 테스트 40개 통과. 노트북 연결·대화·평가·추출 진단과 HWPX 검증을 포함한
최종 확장 회귀 **126개 통과**. Qt 오프스크린 화면에서 기존 파일과 선택 상태,
선택적 업데이트 버튼이 표시되고 처리 진행 표시/워커는 시작되지 않는 것도 확인했다.
실제 사용자 프로젝트 DB나 업로드 파일은 이 수정 과정에서 변경하지 않았다.
다른 AI의 병행 변경은 보존하고, 적용 전에 대상 파일의 해시를 대조했다.
