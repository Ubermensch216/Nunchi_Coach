# 눈치코치 2.0 구현 계획서 — 행동형 업무 비서

- 작성일: 2026-10-10 · 기준 커밋: `211b7eb` · 앱 `0.1.0` · 스키마 **v9**(계획 수립 시점) · 이 문서는 **계획**이다. 진행 상황은 [구현 기록](행동형_업무비서_구현기록_2026-10-10.md)에 적는다. (2026-10-10 현재 0·1단계 일부와 2단계를 구현함.)
- 반영한 자료: 사용자가 제공한 두 문서 — 「눈치코치 2.0 고도화 구상」(이하 **구상**), 「눈치코치 2.0 행동형 AI 비서 구축 설계서」(이하 **설계서**).
- 표기: **확인** = 이 저장소의 코드·문서에서 직접 본 것 / **가설** = 아직 재현·측정하지 않은 것 / **신규** = 지금 없는 것.
- 두 문서 안의 화면 수치(문서 27건, 진행 4건 등), 일정, 부서명은 원문이 스스로 밝힌 대로 **가상 예시**다. 이 계획의 요구사항으로 쓰지 않는다. 외부 링크(대전광역시 평가 결과, Microsoft Learn, NIST, 보도 기사)는 **이번에 열어 확인하지 않았다.** 설계 근거로 인용하지 않으며, 2025년 평가항목 이름은 합성 시험 자료에도 실제 값처럼 쓰지 않는다.

## 1. 결론

1. **구상의 방향은 지금 코드와 맞고, 재료의 절반 이상이 이미 있다.** 반복 주기(`task_cycles`), '지금 챙길 일' 판정(`cycle_format.upcoming`), 과거 사례와 수행 안내의 분리(`task_steps` ↔ `work_steps`·`step_runs`), 공백과 다음 행동(`core/continuity.py`), 근거의 판본 보존(`evidence`), 연도별 절차 비교(`core/compare.py`), 초안 엮기와 다섯 형식 출력(`app/studio/`), 감사 기록(`audit_logs`)이 그것이다. 없는 것은 **① 올해의 수행 건이라는 단위 ② 제안을 저장·거절·중복 방지하는 계층 ③ 여러 도구를 이어 실행하고 승인·재실행을 다루는 실행 엔진 ④ 그 셋을 보여 주는 화면**이다.
2. **두 문서의 구축 순서가 서로 다르다.** 구상 Ⅵ은 "업무기억 정확도 → 선제 브리핑 → 실행" 순이고, 설계서 Ⅺ·Ⅻ는 "3종 산출물 워크플로 먼저 → 선제 제안" 순이다. 이 계획은 **설계서의 순서를 따른다.** 제안은 실행할 것이 있어야 뜻이 있고, 실행 결과의 정확도를 먼저 재야 제안을 얼마나 내도 되는지 정할 수 있기 때문이다. 다만 구상이 1차로 둔 업무기억 보강 가운데 **산출물 A가 직접 의존하는 것**(문서 역할, 연도 구분, 판 관계)은 워크플로 앞에 둔다.
3. **계획·판단을 생성 모델에 맡기지 않는다.** 이 제품의 모델은 CPU에서 도는 `gemma4:e2b`이고 분류 한 건에 2.5초, 통합 분석 한 건에 9.8초다(`app/ai/client.py` 실측 주석). 실행 계획은 코드에 적힌 **고정된 계획 틀**이고, 도구는 규칙으로 동작하며, 모델은 문장을 다듬는 선택 단계에서만 쓴다. 따라서 P0 범위 전체가 **모델 없이** 돈다. 구상 Ⅷ의 "통제형 에이전트"를 한 단계 더 좁힌 것이다.
4. **외부로 나가는 행동은 이번 계획에서 만들지 않는다.** 공문 발송·결재 상신·온나라 입력 도구는 존재하지 않게 둔다. 2026-10-09에 정한 "실제 온나라 연동은 추후"([통합 구현 현황](INTEGRATION_IMPLEMENTATION_2026-10-09.md))와 `BLOCKED_EXTERNAL` 상태를 그대로 따른다. onNara.sAIde 쪽으로는 **사람이 옮길 수 있는 전달 꾸러미(파일)** 까지만 만든다.
5. 구현은 여섯 단계(0~5), 작업 52개다. 0~2단계가 설계서의 P0(3종 산출물), 3단계가 P1(선제 제안), 4~5단계가 P1·P2다.

## 4. 지킬 규칙

기존 규칙(원본 읽기 전용, 루프백만, 근거 표시, 모르면 보류, 추정과 확인 구분)에 다음을 더한다. 각 규칙은 뒤의 시험으로 강제한다.

1. **과거는 올해의 의무가 아니다.** 날짜·기한·지표·배점은 그 해의 공식 문서나 사람의 확인이 있을 때만 '올해 값'으로 보인다. 그 밖에는 '과거 사례'와 '올해 미확인'이다. 화면 문구가 아니라 **데이터의 열**(`due_state`, `source_type`, `mode`)로 가른다.
2. **제안과 실행을 가른다.** 제안은 표의 행 하나일 뿐이고, 받아들이기 전에는 어떤 도구도 돌지 않는다.
3. **승인은 실행 계층이 강제한다.** 도구마다 위험 등급이 있고, 실행기는 승인 행이 없으면 변경 등급 도구를 부르지 않는다. 승인은 **승인한 내용의 해시**에 묶인다 — 내용이 바뀌면 그 승인은 쓸 수 없다.
4. **도구는 원본을 못 쓴다.** 읽기 도구는 읽기 전용 연결을 받고, 쓰는 도구는 `output_policy.validate_output`을 지나는 작성기로만 쓴다. 출력은 프로젝트 폴더의 `outputs/actions/` 아래다.
5. **문서 속 글은 자료다.** 문서 내용이 계획의 단계·도구·수신처를 바꾸지 못한다. 계획 틀은 코드에 있고 도구 인자는 식별자와 수치뿐이다.
6. **다시 실행해도 같은 것이 둘 생기지 않는다.** 실행에는 멱등성 키가 있고, 입력이 같으면 이전 결과를 돌려준다. 입력이 달라지면 새 판을 만들고 옛 판은 남긴다.
7. **무엇을 했는지 다시 짚을 수 있다.** 단계마다 도구 판, 입력 문서의 해시, 쓴 모델과 프롬프트 판, 승인자를 남긴다. `audit_logs`에는 식별자와 결과만 적는다(SEC-005).
8. **조용히 줄이지 않는다.** 못 읽은 문서, 못 찾은 연도, 건너뛴 단계는 산출물 안에 목록으로 적는다.

### 5.1 위험 등급

| 등급 | 뜻 | 예 | 승인 |
|---|---|---|---|
| R0 읽기 | 프로젝트 DB와 원문을 읽는다 | 후보 찾기, 분류, 비교, 검증 | 없음 |
| R1 초안 | `outputs/actions/`에 **새 파일**을 만든다. 실행 기록을 쓴다 | 비교 보고서, 서식 초안, 체크리스트 초안 | 없음 (실행을 받아들인 것이 승인) |
| R2 변경 | 이미 있는 산출물을 확정·교체한다. 업무기억을 바꾼다. 프로젝트 밖의 사용자가 고른 곳에 쓴다 | 서식 배포본 확정, 체크 항목의 담당·기한 확정, 전달 꾸러미 내보내기, 절차 환류 | **단계마다**, 내용 해시에 묶어 |
| R3 외부 | 다른 시스템에 변화를 일으킨다 | 발송, 결재 상신 | **도구 자체를 두지 않는다** |

`registry.register`는 R3 도구를 받으면 예외를 낸다. 실제 연결이 승인·검증된 뒤에 이 제한을 푸는 것은 별도 결정이다.

### 5.2 실행 상태

```
실행(action_runs)   planned → running → waiting_for_approval → running → completed
                                   ↘ failed / partial / cancelled
단계(action_steps)  pending → running → done | failed | skipped | blocked | waiting_for_approval
```

- **멱등성 키** = sha256(계획 틀 이름·판, 업무 id, 대상 연도, 입력 문서 해시의 정렬 목록, 인자). 같은 키의 실행이 있으면 새로 만들지 않고 그것을 연다.
- 단계는 `input_hash`가 같고 `done`이면 다시 돌지 않고 이전 출력을 쓴다. 그래서 실패한 실행의 재실행은 실패한 단계부터 이어진다.
- 앱이 죽으면 `running`으로 남는다. 시작할 때 `running` 단계를 `pending`으로, 실행을 `partial`로 돌리고 작업함에 '이어서 하기'를 보인다. 파일은 임시 이름으로 쓰고 바꿔 끼우므로 반쪽 파일은 남지 않는다(`studio/outputs.export`와 같은 방식).
- 한 번에 하나만 돈다. 모델이 필요한 선택 단계는 분석 파이프라인이 돌고 있으면 기다린다. P0 도구는 모델을 쓰지 않으므로 해당 없다.

## 6. 데이터 모델 — 스키마 v10

`app/db/action_schema.sql`을 새로 두고 `_to_v10`이 `sqlite3.complete_statement`로 끊어 실행한다(`_to_v8`·`_to_v9`와 같은 방식). **기존 표의 행은 바꾸지 않는다.** 승격 전에 `project.db.bak-v9`가 만들어진다. 승격 결과가 새 설치와 같아야 한다는 기존 시험(`test_migrations.py`)을 그대로 통과해야 한다.

```sql
-- 업무기억 보강 (1단계)
CREATE TABLE doc_roles (              -- 문서가 그 업무에서 맡은 역할
  doc_id INTEGER PRIMARY KEY REFERENCES documents(id) ON DELETE CASCADE,
  role TEXT NOT NULL,                 -- directive|criteria|plan|performance|evidence|submission|result|form|other
  basis TEXT NOT NULL DEFAULT '',     -- 판정에 쓴 단서 (파일명 낱말, 제목, 등록본 여부)
  confidence TEXT NOT NULL DEFAULT 'low',
  decided_by TEXT NOT NULL DEFAULT 'ai',
  updated_at TEXT NOT NULL DEFAULT (datetime('now')));

CREATE TABLE doc_years (              -- 한 문서의 여러 '해'. eff_year는 그대로 둔다
  doc_id INTEGER NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  kind TEXT NOT NULL,                 -- authored|performance|evaluation|submitted
  year INTEGER NOT NULL,
  raw TEXT, locator TEXT,             -- 근거가 된 원문과 위치
  decided_by TEXT NOT NULL DEFAULT 'ai',
  PRIMARY KEY (doc_id, kind, year));

-- 수행 건 (0단계)
CREATE TABLE work_cases (             -- "2026년 ○○ 평가 준비" — 올해 실제로 하는 한 건
  id INTEGER PRIMARY KEY,
  task_id INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  period_year INTEGER NOT NULL,
  label TEXT NOT NULL DEFAULT '',
  state TEXT NOT NULL DEFAULT 'open', -- open|closed|not_this_year
  basis_doc_id INTEGER REFERENCES documents(id) ON DELETE SET NULL,  -- 올해 공식 근거 문서
  basis_state TEXT NOT NULL DEFAULT 'unconfirmed',   -- unconfirmed|official|user
  due_date TEXT,
  due_state TEXT NOT NULL DEFAULT 'unknown',         -- unknown|official|user  ('과거 사례'는 여기 들어오지 않는다)
  opened_at TEXT NOT NULL DEFAULT (datetime('now')), closed_at TEXT,
  UNIQUE (task_id, period_year, label));

-- 감지와 제안 (3단계에서 쓰지만 표는 v10에 함께 만든다 — 승격을 한 번으로)
CREATE TABLE signals (
  id INTEGER PRIMARY KEY, kind TEXT NOT NULL,        -- time|event|gap|conversation
  task_id INTEGER REFERENCES tasks(id) ON DELETE CASCADE,
  signal_key TEXT NOT NULL UNIQUE,                   -- 같은 신호를 두 번 적지 않는다
  detail TEXT NOT NULL DEFAULT '{}',                 -- 식별자·수치만. 본문 없음
  detected_at TEXT NOT NULL DEFAULT (datetime('now')));

CREATE TABLE recommendations (
  id INTEGER PRIMARY KEY,
  signal_id INTEGER REFERENCES signals(id) ON DELETE SET NULL,
  task_id INTEGER REFERENCES tasks(id) ON DELETE CASCADE,
  target_year INTEGER, plan_key TEXT NOT NULL,
  rec_key TEXT NOT NULL UNIQUE,                      -- (업무, 계획 틀, 연도, 신호 갈래)의 지문
  certainty TEXT NOT NULL DEFAULT 'precedent',       -- official|precedent|suggested
  state TEXT NOT NULL DEFAULT 'new',                 -- new|seen|accepted|dismissed|snoozed|expired|superseded
  snooze_until TEXT, dismiss_reason TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')), decided_at TEXT);

-- 실행 (0단계)
CREATE TABLE action_runs (
  id INTEGER PRIMARY KEY,
  case_id INTEGER REFERENCES work_cases(id) ON DELETE SET NULL,
  task_id INTEGER REFERENCES tasks(id) ON DELETE SET NULL,
  recommendation_id INTEGER REFERENCES recommendations(id) ON DELETE SET NULL,
  plan_key TEXT NOT NULL, plan_version TEXT NOT NULL,
  idem_key TEXT NOT NULL UNIQUE,
  params TEXT NOT NULL DEFAULT '{}',
  state TEXT NOT NULL DEFAULT 'planned',
  started_at TEXT, finished_at TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')));

CREATE TABLE action_steps (
  id INTEGER PRIMARY KEY,
  run_id INTEGER NOT NULL REFERENCES action_runs(id) ON DELETE CASCADE,
  ordinal INTEGER NOT NULL, step_key TEXT NOT NULL DEFAULT '',   -- 계획 틀 안에서의 단계 이름
  tool TEXT NOT NULL, tool_version TEXT NOT NULL, risk TEXT NOT NULL,
  state TEXT NOT NULL DEFAULT 'pending',
  input_hash TEXT, output TEXT NOT NULL DEFAULT '{}',   -- 다음 단계로 넘기는 식별자·수치
  model TEXT NOT NULL DEFAULT '', prompt_version TEXT NOT NULL DEFAULT '',
  attempts INTEGER NOT NULL DEFAULT 0, error TEXT,
  started_at TEXT, finished_at TEXT,
  UNIQUE (run_id, ordinal));

CREATE TABLE action_approvals (
  id INTEGER PRIMARY KEY,
  run_id INTEGER NOT NULL REFERENCES action_runs(id) ON DELETE CASCADE,
  step_id INTEGER REFERENCES action_steps(id) ON DELETE CASCADE,
  action TEXT NOT NULL,                              -- 무엇을 승인했는가 (도구 이름)
  scope_hash TEXT NOT NULL,                          -- 승인한 내용의 지문
  decision TEXT NOT NULL,                            -- approved|rejected
  approver_name TEXT NOT NULL DEFAULT '', approver_role TEXT NOT NULL DEFAULT 'successor',
  note TEXT, decided_at TEXT NOT NULL DEFAULT (datetime('now')));

CREATE TABLE artifacts (
  id INTEGER PRIMARY KEY,
  run_id INTEGER REFERENCES action_runs(id) ON DELETE SET NULL,
  step_id INTEGER REFERENCES action_steps(id) ON DELETE SET NULL,
  case_id INTEGER REFERENCES work_cases(id) ON DELETE SET NULL,
  kind TEXT NOT NULL,       -- comparison|evidence_list|open_questions|collection_form|form_guide|form_check|checklist|request_draft|report_draft|handoff
  title TEXT NOT NULL,
  mode TEXT NOT NULL DEFAULT 'preliminary',          -- preliminary(사전조사용)|official(공식 기준 반영)
  basis_year INTEGER,
  format TEXT NOT NULL, path TEXT NOT NULL, sha256 TEXT NOT NULL,
  source_snapshot TEXT NOT NULL DEFAULT '[]',        -- [{doc_id, hash}] 만들 때 본 문서의 판
  state TEXT NOT NULL DEFAULT 'draft',               -- draft|reviewed|final|stale|superseded
  version INTEGER NOT NULL DEFAULT 1,
  supersedes_id INTEGER REFERENCES artifacts(id) ON DELETE SET NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now')));

CREATE TABLE checklist_items (
  id INTEGER PRIMARY KEY,
  case_id INTEGER NOT NULL REFERENCES work_cases(id) ON DELETE CASCADE,
  run_id INTEGER REFERENCES action_runs(id) ON DELETE SET NULL,
  work_step_id INTEGER REFERENCES work_steps(id) ON DELETE SET NULL,
  slot TEXT NOT NULL,                                -- 다시 만들 때 같은 항목을 찾는 이름
  code TEXT NOT NULL DEFAULT '', ordinal INTEGER NOT NULL DEFAULT 0,
  phase TEXT NOT NULL DEFAULT '',                    -- 기준 확인|자료 준비|자료 수합|보고 준비
  title TEXT NOT NULL, description TEXT NOT NULL DEFAULT '',
  source_type TEXT NOT NULL,                         -- official|stated|precedent|suggested|user
  assignee TEXT NOT NULL DEFAULT '',
  due_date TEXT, due_state TEXT NOT NULL DEFAULT 'unknown',
  depends_on INTEGER REFERENCES checklist_items(id) ON DELETE SET NULL,
  approval_required INTEGER NOT NULL DEFAULT 0,
  state TEXT NOT NULL DEFAULT 'todo',                -- todo|doing|review|done|skipped
  completion_kind TEXT, completion_ref TEXT,         -- user | system(artifact id·step id)
  origin TEXT NOT NULL DEFAULT 'auto',               -- auto|user  (사람이 고친 것은 다시 만들 때 덮지 않는다)
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  UNIQUE (case_id, slot));
```

덧붙이는 것:

- 근거는 기존 `evidence` 표를 쓴다. `owner_kind`에 `rec`·`check`·`artifact`를 더하고 삭제 방아쇠 셋을 추가한다. 근거의 모양(문서 판 해시·위치·인용문)이 제품 전체에서 하나로 남는다.
- `task_items.kind`에 `output`(산출물)·`regulation`(관련 규정)·`risk`(위험)·`agency`(관계기관)를 더한다. 열 변경은 없다(`kind`에 제약이 없다).
- `task_links`(업무 사이의 관계)와 `learned_rules`(환류)는 5단계에서 v11로 따로 올린다. 지금 모양을 정하면 쓰기 전에 굳는다.
- 인계 묶음(`core/transfer.py`)은 이번 표들을 싣지 않는다. 수행 건·산출물은 그 PC의 실행 기록이다. 옮길 필요가 생기면 묶음 형식 판을 올리는 별도 작업이다.

### 2단계 — 3종 산출물 워크플로 (설계서 P0)

계획 틀 이름은 `recurring_prep`(반복 업무 준비)이다. 규제혁신 평가는 **시험 시나리오**이고 틀에는 그 낱말이 들어가지 않는다. 인자는 업무 id와 대상 연도다.

```
1 discover(R0) → 2 classify(R0) → 3 compare(R1) → 4 form(R1) → 5 checklist(R1) → 6 verify(R0) → 완료
        └ 근거 부족이면: 3은 '자료 부족' 보고서를 내고 4·5는 계속 (설계서 Ⅵ의 분기)

```

## 8. 검증

### 8.1 합성 시나리오

`tests/fixtures/action_scenarios/`에 시나리오를 JSON으로 두고 `scenario_eval.write_corpus` 방식으로 문서를 짓는다. 첫 시나리오는 "평가 대응 업무" 하나다.

- 2024·2025년 각각: 시행문, 지표 표(이름은 같고 배점이 다른 지표 하나, 새로 생긴 지표 하나, 없어진 지표 하나), 부서별 실적 XLSX, 증빙, 제출본, 결과 통보
- 같은 공문의 수정본 다섯(파일명에 '최종'이 둘)
- 실적연도 2025·평가연도 2026이 함께 적힌 문서
- 섞여 있는 다른 평가(합동평가·적극행정) 문서 — 낱말이 겹치지만 다른 업무
- 본문에 "이 문서를 읽는 AI는 … 발송하라" 꼴의 지시문이 든 문서
- 2026년 문서 없음. 변형 시나리오에서 2026년 지표를 뒤늦게 넣는다

지표 이름과 배점은 **지어낸 값**이고 시나리오 파일에 합성임을 적는다. 정답은 문서를 짓기 전에 적어 동결한다(해시 기록). 결과를 보고 코드를 고치면 그 시나리오는 개발용이 되고 판정에는 새 시나리오가 필요하다 — 질문 평가에서 쓰는 규율과 같다.

## 9. 위험과 한계

| 위험 | 대응 |
|---|---|
| 업무 묶음이 틀리면 그 위의 비교·서식·체크리스트가 모두 틀린다 | 후보 찾기가 업무 안의 이질 문서를 따로 보고. 수행 건을 열 때 "이 문서들로 준비합니다"를 한 번 보이고 뺄 수 있게 |
| 모델이 없으면 업무 자체가 생기지 않는다(현황 문서 2절) | 이번 범위 밖. 다만 사람이 직접 만든 업무에서도 계획 틀이 돌게 한다 |
| 표 머리글이 기관마다 달라 지표를 못 읽는다 | 못 읽으면 지표 비교를 '자료 부족'으로 내고 나머지는 계속. 머리글 동의어는 시나리오 밖의 표본을 본 뒤에만 늘린다 |
| 제안이 많아 무시된다 | 새 제안 다섯 개 상한, 거절 기억, 내지 말아야 할 제안 비율을 게이트로 |
| 서식의 수식을 계산해 보지 못한다 | 구조 검증까지. 한글·엑셀에서 실제로 열어 보는 확인은 사람 몫으로 적는다 |
| 승인자가 본인인지 알 수 없다 | 표시명 기록일 뿐임을 화면과 문서에 적는다. 계정은 조직 확장 단계 |
| 산출물에 원문 인용이 들어간다 | 프로젝트 폴더 안에만. 전달 꾸러미에는 `transfer.NOTICE` 같은 안내. 암호화는 없다(기존 한계) |
| `tasks.py`·`repo.py`가 더 커진다 | 새 화면·새 믹스인으로만. 기존 파일에는 단추와 호출만 |
| 모델 요약 단계가 느리다(CPU) | 기본은 끔. 켜도 산출물은 규칙 본문만으로 완성돼 있다 |

## 10. 정해야 할 것

착수 전에 정하면 되돌아가지 않는 것들이다. **2026-10-10 사용자 결정**: 전부 권고안대로 진행한다. D4(sAIde 전달 형식)는 미확정이므로 **H6을 뒤로 미룬다**. D7(실자료 표본)은 없이 **합성 자료로 진행하고 나중에 보강**한다.

## 11. 착수 순서

첫 변경 단위는 **F1 → F2 → F4 → F7(가짜 도구)** 이다. 화면도 산출물도 없이 "실행기가 승인 없이 변경 도구를 부르지 않는다"와 "다시 돌려도 둘이 되지 않는다"를 먼저 시험으로 고정한다. 그다음 F3·F5·F6·F9, M1~M4, A1~A4 순으로 올라가며 E1의 시나리오를 A1 전에 동결한다.

단계마다 끝에 하는 일은 기존과 같다 — 전체 회귀, `lockfile --check`, 기록 문서(이 계획은 고치지 않고 `구현진행` 형식의 기록을 따로 덧붙임), [현재 구현 및 검증 현황](현재구현_및_검증현황.md) 갱신.

중단 조건은 [IMPLEMENTATION_PLAN](IMPLEMENTATION_PLAN.md) 5절을 그대로 쓰고 둘을 더한다 — **승인 없이 변경·외부 등급 동작이 실행되는 경로를 발견했을 때**, **과거 값이 올해 값으로 표시되는 경로를 발견했을 때**.
