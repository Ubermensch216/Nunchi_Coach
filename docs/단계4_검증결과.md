# 단계 4 검증 결과 — 평가·패키징

실행일: 2026-10-06 · 기준: 단계별 구축 계획서 3.0 §6 단계 4, §7

이 문서는 **이 장비 한 대에서, 합성 자료로** 확인한 것만 적는다. 계획서의 완료 기준 G4(깨끗한 PC·제3자 실행·실제 기관 연결)는 충족하지 않았다. 무엇을 하지 못했는지는 맨 아래에 따로 적었다.

## 환경

| 항목 | 값 |
|---|---|
| OS | Windows 11 Pro 10.0.26200 |
| Python | 3.14.7, `requirements.lock`과 일치(`python -m app.tools.lockfile --check`) |
| Ollama 모델 | 생성 `gemma4:e2b`(5.1B, Q4_K_M, 사고 기능 있음), 임베딩 `bge-m3`(F16) |
| 자료 | 합성 표본(`tests/fixtures/sample_tree`, 76건) + 시나리오 합성 자료 13건. 실제 기관 문서 없음 |

장비의 CPU/GPU/RAM 사양과 최대 메모리 사용량은 기록하지 않았다.

## 1. 전체 회귀

잠금 환경에서 `python -m pytest`: **1102 통과 · 0 실패 · 4 건너뜀**(7분 36초). 건너뜀 4건은 실제 모델이 필요한 시험 2건과 표본이 필요한 조건부 시험이다.

## 2. 업무 수행 시나리오 평가 (모델 없음, 결정적)

`python -m app.tools.scenario_eval` — 빈 프로젝트에 원문 폴더만 넣고, 사람이 아무것도 입력하기 전의 결과를 정답(`tests/fixtures/scenarios/answers.json`)과 견준다. 정답은 평가 도구만 읽는다.

| 시나리오 | 자동 복원 | 그 밖의 검사 |
|---|---|---|
| 정기 실적 보고 (자료 충분) | 12/13 | 모두 통과 |
| 진행 중 계약·정산 (완료 여부 누락) | 5/7 | 모두 통과 |
| 개정된 절차와 반복 업무 | 7/8 | 모두 통과 |
| **합계** | **24/28 (86%)** | 검사 95건 중 실패 0 · 오판 0 |

- **자동 복원율은 계획서 기준 90%에 미치지 못한다.** 놓친 4건은 모두 이름표 없이 문장으로만 적힌 내용이다(정산 기한 “준공검사 뒤 30일 이내”, 진행 상태 “1차 기성금 지급”, 시행일 “4월 1일 이후 접수분부터”, 작성 요령). 규칙 기반 추출의 한계이며 분모에서 빼지 않았다.
- 오판 방지: 과거 제출일·지난해 계약금액·개정 전 서식을 현재 값으로 내놓지 않았고, 후속 문서가 없다는 이유로 완료·미완료·지연을 단정하지 않았다.
- 공백 대응: 공백마다 구체적인 다음 행동이 있고, ‘전임자에게 문의’로 끝나는 문구가 없으며, 공백이 자기 단계만 막는다.
- 전임자 독립성: 세 시나리오 모두 전임자 정보·사람의 확인 0회로 복원본이 저장됐다.
- 업무 연속성: 단계를 기록하고 프로젝트를 닫았다 열어 다시 분석해도 기록이 남았다.
- 원본 보호: 분석·저장 전후 원본 해시가 같다.

읽을 때 주의: 문서를 업무에 묶는 일은 건너뛰고 직접 배정했다(아래 4절 참고). 합성 자료 세 건이며 정답도 같은 사람이 만들었다. 실제 기관 문서에서의 수치가 아니다.

### 이 평가가 드러내 고친 결함

| 결함 | 조치 |
|---|---|
| 올해 진행 중인 문서 2건을 ‘과거 수행 사례’로 내밀어 지난해의 끝까지 간 순서가 가려짐 | 기준 연도보다 앞선 가장 최근 회차를 쓰도록 변경 |
| 과거 사례만 있는 업무에서 끝냈다고 기록한 단계를 다음 행동으로 다시 권함 | 완료한 사례는 건너뜀 |
| 개정 전후 지침이 있을 때 최근 값만 올리고 이전 값을 감춤 | ‘이전과 다름’ 공백으로 양쪽을 나란히 보이고 확정하지 않음 |
| 받는 기한(신청기한)과 ‘통보’ 단계를 제출처·제출기한에 걸어 엉뚱한 단계를 막음 | 내는 단계와 우리가 지킬 기한에만 연결 |

## 3. 실제 모델 확인

### 3.1 짧은 이름 생성 (B06)

`gemma4:e2b`로 업무 이름 짓기를 3회 호출했다.

| 조건 | 결과 | 시도 | 생성 토큰 | 시간 |
|---|---|---|---|---|
| 사고 기능 끔(제품 동작) | 3회 모두 이름 생성 | 1 | 43~49 | 2.5~8.9초 |
| 사고 기능을 끄지 않음(견주기) | 첫 시도는 한도 200을 다 쓰고 빈 응답 → 한도 800으로 재시도해 생성 | 2 | 509 | 38.9초 |

사고 과정이 생성 한도를 소진해 빈 응답이 나오는 현상, 이를 피하는 `think=false`, 그래도 비었을 때의 재시도가 모두 실제 모델에서 확인됐다.

### 3.2 전체 분석 1회

합성 표본과 시나리오 자료 90건: **78초**(의미 색인 22초, 업무 파악 33초, 질문 준비 21초, 나머지 2초 미만). 읽기 실패 0, 업무 7개, 조각 154개 모두 임베딩, 원본 불변.

### 3.3 질문 평가 (`rag_report`, 9문항 × 3회, 2차례)

| 지표 | 결과 |
|---|---|
| 유보 정확도(없는 것을 지어내지 않음) | 3/3, 6회 반복 모두 |
| 응답 정확도 | 5/6 |
| 인용 전량 나열 | 0 |
| 응답 시간 | 중앙값 5.2초 · 최대 15.5초 |
| 근거 없는 금액·기한 확정 | 0 |

- **불안정한 문항 1건**: “2023년 예산 요구액이 얼마야?”가 전체 실행에서는 3회 모두 답하지 못했고, 따로 돌렸을 때는 3회 모두 옳게 답했다. 프롬프트는 글자 하나까지 같았다. 답하지 못한 경우 모델은 `answered: true`에 빈 문장 목록을 돌려줬고, 온도를 바꾸거나 다시 물어도 그 상태에서는 같았다. 모델이 다시 적재되는 등의 상태에 따라 갈리는 것으로 보이나 원인을 확정하지 못했다.
- 이 경우 제품은 틀린 답을 내지는 않는다. 다만 예전에는 ‘확인 가능한 자료가 부족합니다’로 보여 줬는데, 자료는 있고 생성이 실패한 것이므로 ‘모델이 답변 문장을 만들지 못했습니다’로 구분해 보이도록 고쳤다.
- 문항 수가 9개다. 계획서의 개발용 30문항·최종 60문항 평가는 만들지 않았다. p95 지연을 말할 표본도 아니다.

### 3.4 실제 모델 실행이 드러낸 결함

| 결함 | 조치 |
|---|---|
| 분석이 다시 돌 때 ‘업무 파악’이 아직 확인하지 않은 업무를 지우고 새로 만들면서, 그 업무의 사람 수정·수행 기록·닫은 공백이 연쇄로 함께 지워짐 | 사람이 무엇이든 해 둔 업무는 지우지 않고 문서 배정도 유지. 회귀 시험 5종 추가 |
| 생성 실패(빈 문장 목록)를 ‘자료 부족’으로 표시 | 생성 실패로 구분해 표시 |

## 4. 업무 묶기와 복원의 관계 — 미해결

실제 모델로 묶었을 때 시나리오 자료 세 묶음 중 **두 묶음(계약·정산 5건, 보조금 교부 4건)이 어느 업무에도 묶이지 않았다.** 정기 실적보고는 4건 중 3건이 한 업무로 묶여 문서에 적힌 절차 4단계와 항목이 복원됐다.

업무 복원은 업무에 묶인 문서에서만 일어난다. 따라서 묶이지 않은 문서들에는 ‘지금 할 일’ 카드가 생기지 않는다. 문서 수가 적거나 형식이 섞인 업무에서 이런 일이 생긴다. 2절의 시나리오 평가는 직접 배정으로 이 단계를 건너뛰었으므로 이 문제를 보여 주지 않는다.

지금 가능한 우회는 사람이 문서 화면에서 미분류 문서를 업무에 배정하는 것이다. 군집 기준을 낮추거나, 미분류 문서 묶음에도 복원을 돌리는 것은 정하지 않았다 — 기준을 낮추면 기존에 보정한 업무 분류가 흐트러질 수 있어 실제 자료로 재 봐야 한다.

| 항목 | 결과 |
|---|---|
| 빌드 | `python -m PyInstaller NunchiCoach.spec` 성공(약 70초), `dist/NunchiCoach/` 217MB |

| 업무 복원 자체 점검 | 같은 명령에 추가(`app/tools/selfcheck.py`). 빌드한 실행물 안에서 복원 → 수행 기록 → 복원본 → 묶음 → 가져오기 → 재연결이 통과했다 |

**빌드한 장비에서만 실행했다.** Python이 없는 깨끗한 PC에서의 실행, 화면을 띄운 실행, 설치 안내서대로의 제3자 실행은 하지 않았다. `.hwp`(HWP 5.0)는 표본이 없어 점검하지 못했다.

## 7. 실패 상황 점검 (자동 시험으로 확인한 범위)

| 상황 | 확인 |
|---|---|
| Ollama 꺼짐·모델 없음 | 파싱·시점·일정·처리 순서·업무 복원은 계속 동작, 질문은 연결 오류로 구분 표시 |
| 생성 한도 초과·빈 응답·잘린 응답 | 종류별로 구분, 빈 응답은 1회 재시도, 잘린 응답은 완성된 문장만 건짐 |
| 취소 | 통신 중단, 멈춘 단계를 완료로 적지 않음 |
| 강제 종료 | 실제 프로세스 강제 종료 뒤 DB 정합성 통과·재개, 문서 단위 기록 원자화 |
| 자료 이동·원문 개정·누락·중복 사본 | 재연결 6종 시험 |

인터넷이 끊긴 상태에서의 실행은 따로 해 보지 않았다(코드는 루프백 주소 외에는 거부한다).

## 하지 못한 것 (G4 미충족 항목)

1. **깨끗한 PC 실행**: Python 없는 별도 Windows PC에서의 실행과 최소 사양 측정.
2. **제3자 실행**: 개발자가 아닌 사람이 안내서만 보고 첫 업무를 수행하는 시험과 소요 시간 비교.
3. **실제 온나라 연결**: 기관 환경이 없어 직접 수집은 미구현·미검증이다. 합성 연결부만 있다. 계획서 기준으로 온나라 직접 수집 P0는 미완료다.
4. **실제 기관 문서**: 실제 한글 저장 HWPX(대회 안내서 2건 포함)와 HWP 5.0으로의 검증.
5. **평가셋**: 개발용 30문항·최종 60문항과 두 번째 모델.
6. **성능 측정**: 장비 사양 기록, 질문 지연 p50/p95, 최대 메모리, 취소 응답 시간.
7. **효과 측정**: 수작업 대비 시간·누락 비교.
8. **화면 사용 확인**: ‘지금 할 일’·복원본 대화상자는 시험 코드로 눌렀고 사람이 써 본 것이 아니다.
9. **라이선스 방침 결정**(6절).
