## 2. 업무 수행 시나리오 평가 (모델 없음, 결정적)

`python -m app.tools.scenario_eval` — 빈 프로젝트에 원문 폴더만 넣고, 사람이 아무것도 입력하기 전의 결과를 정답(`tests/fixtures/scenarios/answers.json`)과 견준다. 정답은 평가 도구만 읽는다.

| 시나리오 | 자동 복원 | 그 밖의 검사 |
|---|---|---|
| 정기 실적 보고 (자료 충분) | 12/13 | 모두 통과 |
| 진행 중 계약·정산 (완료 여부 누락) | 5/7 | 모두 통과 |
| 개정된 절차와 반복 업무 | 7/8 | 모두 통과 |
| **합계** | **24/28 (86%)** | 검사 95건 중 실패 0 · 오판 0 |

- **자동 복원율은 계획서 기준 90%에 미치지 못한다.** 놓친 4건은 모두 이름표 없이 문장으로만 적힌 내용이다(정산 기한 “준공검사 뒤 30일 이내”, 진행 상태 “1차 기성금 지급”, 시행일 “4월 1일 이후 접수분부터”, 작성 요령). 규칙 기반 추출의 한계이며 분모에서 빼지 않았다.
- 오판 방지: 과거 제출일·지난해 계약금액·개정 전 서식을 현재 값으로 내놓지 않았고, 후속 문서가 없다는 이유로 완료·미완료·지연을 단정하지 않았다.
- 공백 대응: 공백마다 구체적인 다음 행동이 있고, ‘전임자에게 문의’로 끝나는 문구가 없으며, 공백이 자기 단계만 막는다.
- 전임자 독립성: 세 시나리오 모두 전임자 정보·사람의 확인 0회로 복원본이 저장됐다.
- 업무 연속성: 단계를 기록하고 프로젝트를 닫았다 열어 다시 분석해도 기록이 남았다.
- 원본 보호: 분석·저장 전후 원본 해시가 같다.

**모델을 넣은 실행(`--model`, gemma4:e2b)**: 28/28, 검사 95건 실패 0 · 오판 0(2회 같은 결과). 놓쳤던 4문장을 ‘문장에서 찾은 내용’(추정)으로 내놓았다. 이 수치는 재현율만 보여 준다 — 시나리오 자료에는 후보 문장이 1~2개뿐이고 모두 정답이라 엉뚱한 문장을 고르는지는 드러나지 않는다. 합성 표본을 섞은 전체 분석에서는 문장 6건 중 2건이 쓸모없는 틀 문장이었다(3.2절). 기본 실행의 86%를 대신하는 수치가 아니다.

읽을 때 주의: 문서를 업무에 묶는 일은 건너뛰고 직접 배정했다(아래 4절 참고). 합성 자료 세 건이며 정답도 같은 사람이 만들었다. 실제 기관 문서에서의 수치가 아니다.

| 결함 | 조치 |

## 3. 실제 모델 확인

|---|---|---|---|---|

### 3.2 전체 분석 1회

합성 표본과 시나리오 자료 90건: **78초**(의미 색인 22초, 업무 파악 33초, 질문 준비 21초, 나머지 2초 미만). 읽기 실패 0, 업무 7개, 조각 154개 모두 임베딩, 원본 불변.

재실행(문장 추출·파일명 묶기 추가 뒤, 같은 90건): **98초**(의미 색인 23초, 업무 파악 22초, 업무 복원 29초, 질문 준비 23초). 업무 8개 · 배정 87건 · 파일명으로 묶은 제안 2개(‘용역’ 5건, ‘보조금’ 4건, 둘 다 확신 낮음) · 미분류 3건. 문장에서 찾은 내용 6건 — 시나리오의 문장 4건과, 걸러지지 않은 틀 문장 2건(“본 문서는 … 단계에서 작성되었다”). 틀 문장을 거르기 전에는 25건이었다. ‘업무 복원’ 단계는 모델 호출 때문에 2초 미만에서 29초로 늘었다(같은 문장 묶음은 다음 분석에서 다시 묻지 않는다).

### 3.3 질문 평가 (`rag_report`, 9문항 × 3회, 2차례)

| 지표 | 결과 |
|---|---|
| 유보 정확도(없는 것을 지어내지 않음) | 3/3, 6회 반복 모두 |
| 응답 정확도 | 5/6 |
| 인용 전량 나열 | 0 |
| 응답 시간 | 중앙값 5.2초 · 최대 15.5초 |
| 근거 없는 금액·기한 확정 | 0 |

- **불안정한 문항 1건**: “2023년 예산 요구액이 얼마야?”가 전체 실행에서는 3회 모두 답하지 못했고, 따로 돌렸을 때는 3회 모두 옳게 답했다. 프롬프트는 글자 하나까지 같았다. 답하지 못한 경우 모델은 `answered: true`에 빈 문장 목록을 돌려줬고, 온도를 바꾸거나 다시 물어도 그 상태에서는 같았다. 모델이 다시 적재되는 등의 상태에 따라 갈리는 것으로 보이나 원인을 확정하지 못했다.
- 이 경우 제품은 틀린 답을 내지는 않는다. 다만 예전에는 ‘확인 가능한 자료가 부족합니다’로 보여 줬는데, 자료는 있고 생성이 실패한 것이므로 ‘모델이 답변 문장을 만들지 못했습니다’로 구분해 보이도록 고쳤다.
- 위 수치는 9문항 기준이다.

### 3.3-1 개발용 30문항 (`rag_report --dev`, 30문항 × 2회)

기본 9문항에 21문항을 더했다(답해야 하는 질문 19 · 유보해야 하는 질문 11). 자료는 3.2절 재실행의 90건이다.

| 지표 | 보완 전 | 빈 답 재질문 보완 뒤 |
|---|---|---|
| 통과 | 20/30 | **25/30** (2회 모두) |
| 응답 정확도 | 13~14/19 | 17/19 |
| 유보 정확도 | 10/11 | 9/11 |
| 생성 실패(답할 수 있다면서 문장 없음) | 6~7문항 | 0 |
| 실행마다 갈리는 문항 | 4 | 0 |
| 응답 시간 | 중앙값 6.6초 · p95 약 21초 | 중앙값 6.8~7.1초 · p95 약 21초 · 최대 23.8초 |

- **생성 실패가 9문항에서 본 것보다 훨씬 잦았다**(30문항 중 6~7). 모델이 `answered: true`에 빈 문장 목록을 돌려주는 경우다. 문장을 하나 이상 내도록 문법을 좁혀 한 번만 다시 묻게 했고(받은 문장은 근거 검증을 그대로 거친다), 이후 2회 실행에서 생성 실패는 0이었다.
- **보완의 값**: 유보 정확도가 10/11에서 9/11로 내려갔다. `wrong-task-hallucination`(“계약관리 업무는 어떤 순서로 처리해?”)이 예전에는 생성 실패로 끝났는데, 이제는 시나리오 자료의 실제 문장 “대금은 준공검사를 마친 뒤 30일 이내에 정산한다.”를 근거와 함께 답한다. 없는 내용을 지어낸 것은 아니지만 ‘순서’를 묻는 질문에 대한 답도 아니다. 이 문항은 합성 표본만 있을 때를 전제로 만든 것이라 시나리오 자료를 섞은 지금은 전제가 달라졌다. 그래도 유보해야 할 질문에 답이 나간 것으로 센다.
- **보완 전후 모두 실패한 문항 4개**:
  - `absent-reason` “예산 집행액이 2분기에 적었던 이유가 뭐야?” → “2분기 집행액은 430입니다.” **이유를 묻는데 숫자로 답했고 그 숫자도 틀렸다**(표에서 2분기는 210, 430은 3분기). 근거 검증은 430이 근거에 있으므로 통과시켰다. 표의 열을 잘못 읽은 답을 검증이 잡지 못한다는 뜻이다. 이 평가에서 가장 무거운 결함이다.
  - `sheet-other-row` “예산 집행액은 3분기에 얼마였어?” → 기대한 문서를 근거로 잡지 못했고 430을 답하지 못했다.
  - `sheet-compare`(네 분기 값 견주기)와 `yearly-cycle`(여러 해에 걸친 반복 시기)는 유보했다.
- 문항과 정답을 같은 사람이 합성 표본에 맞춰 만들었다. 2회 반복이며 계획서의 3회 이상 권고에 못 미친다. 최종 60문항과 두 번째 모델은 하지 않았다.

## 4. 업무 묶기와 복원의 관계 — 우회 경로 추가

실제 모델로 묶었을 때 시나리오 자료 세 묶음 중 **두 묶음(계약·정산 5건, 보조금 교부 4건)이 어느 업무에도 묶이지 않았다.** 정기 실적보고는 4건 중 3건이 한 업무로 묶여 문서에 적힌 절차 4단계와 항목이 복원됐다.

업무 복원은 업무에 묶인 문서에서만 일어난다. 따라서 묶이지 않은 문서들에는 ‘지금 할 일’ 카드가 생기지 않는다. 문서 수가 적거나 형식이 섞인 업무에서 이런 일이 생긴다. 2절의 시나리오 평가는 직접 배정으로 이 단계를 건너뛰었으므로 이 문제를 보여 주지 않는다.

(위는 처음 확인했을 때의 상태다.)

**조치**: 군집 기준은 그대로 두고, 벡터로 묶이지 않고 남은 문서만 파일명의 첫 낱말이 같은 것끼리 3건 이상일 때 ‘낮은 확신’의 업무 제안으로 올린다. 이미 있는 업무에는 밀어 넣지 않는다. 재실행에서 두 묶음이 ‘용역’(5건)·‘보조금’(4건) 제안으로 올라왔고 복원 카드가 생겼다(용역: 항목 4개와 과거 사례, 보조금: 문서에 적힌 절차 4단계). 정기 실적보고의 4건은 표본의 월간실적보고와 한 업무(‘실적보고’ 27건)로 묶였다.

남은 것: 이 경로는 파일명 첫 낱말이 업무를 가리킬 때만 통한다. 파일명이 제각각인 실제 자료에서는 재지 않았다. 묶이지 않은 문서는 여전히 사람이 문서 화면에서 배정해야 한다.

## 5. 실행물

| 항목 | 결과 |
|---|---|
| 빌드 | `python -m PyInstaller NunchiCoach.spec` 성공(약 85초), `dist/NunchiCoach/` 218MB |
| 오픈소스 고지 | 빌드가 `THIRD_PARTY_NOTICES.txt`를 다시 만들어 실행물 안과 실행 파일 옆에 넣는다. `NunchiCoach.exe licenses` 출력 확인(7,111줄). 고지문이 없으면 `selftest`가 실패한다 |
| 파서 자체 점검 | `NunchiCoach.exe selftest tests/fixtures/sample_tree` 통과(hwpx·pdf·xlsx 본문 추출 100%) |
| 업무 복원 자체 점검 | 같은 명령에 추가(`app/tools/selfcheck.py`). 빌드한 실행물 안에서 복원 → 수행 기록 → 복원본 → 묶음 → 가져오기 → 재연결이 통과했다 |

**빌드한 장비에서만 실행했다.** Python이 없는 깨끗한 PC에서의 실행, 화면을 띄운 실행, 설치 안내서대로의 제3자 실행은 하지 않았다. `.hwp`(HWP 5.0)는 표본이 없어 점검하지 못했다.

## 6. 구성요소와 라이선스

**방침(2026-10-06 결정)**: PyMuPDF는 교체하지 않고 AGPL-3.0 조건으로 쓴다. 실행물에 든 구성요소와 빌드·시험 도구를 모두 고지한다.

`python -m app.tools.notices`가 SBOM과 같은 34개 구성요소(실행물 포함 21 · 빌드·시험 도구 13)의 고지문을 만든다.

| 구성요소 | 표기된 라이선스 | 고지문에 적은 것 |
|---|---|---|
| PyMuPDF 1.28.2 (MuPDF 포함) | AGPL-3.0 또는 Artifex 상용 | AGPL-3.0으로 쓴다는 것, 상용 라이선스를 쓰지 않는다는 것, 이 프로그램과 PyMuPDF·MuPDF의 소스 위치 |
| PySide6 / shiboken6 6.11.1 (Qt 6) | LGPL-3.0 또는 GPL | 고치지 않았고 동적 라이브러리로 따로 들어 있어 바꿔 넣을 수 있다는 것, 소스 위치 |
| PyInstaller 6.22.0 | GPL-2.0-or-later(부트로더 예외) | 빌드 도구이며 실행물에는 부트로더만 들어간다는 것 |

| 나머지 | MIT·BSD·Apache·MPL·PSF 계열 | 이름·판·라이선스·출처와 배포판이 준 본문 |

**아직 채워지지 않은 것**

1. **AGPL-3.0·LGPL-3.0·GPL-3.0 본문이 고지문에 없다.** 배포판에 들어 있지 않기 때문이다. 지금은 받는 주소만 적히고 빌드가 경고한다. `app/licenses/texts/`에 세 파일을 넣으면 실린다.
2. **소스 제공**: AGPL-3.0은 실행물을 받은 사람이 이 프로그램의 대응 소스를 받을 수 있어야 한다. 고지문은 저장소 주소를 적었지만, 저장소의 공개 여부와 저장소 자체의 `LICENSE` 표기는 확인·결정하지 않았다.
3. Qt가 안에 포함하는 제3자 구성요소는 목록 주소만 적었다.

**이 표와 고지문은 패키지가 스스로 밝힌 표기를 옮긴 것이며 법적 검토가 아니다.**
