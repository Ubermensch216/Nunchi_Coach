### P0-01 청크 생성과 임베딩 분리 — `INVESTIGATING` → 구현 대상

**설계**

1. `Pipeline._chunks`를 두 구간으로 나눈다.
   - (가) 조각 만들기: `health()`를 보지 않고 항상 실행. `document_sections` → `build_chunks` → `replace_document_chunks`. 조각 FTS는 `chunks` 트리거가 이미 채운다(`schema.sql:258-270`).
   - (나) 임베딩: `embedding_ready`일 때만. 아니면 "조각 N개 준비 · 임베딩 보류 — {사유}"로 보고하고 끝낸다.
2. 대상 선정 질의를 분리한다. (가)는 조각이 없는 문서만(`documents_without_chunks` 신설), (나)는 기존 `documents_needing_chunks(model)`·`chunks_needing_embedding` 그대로.
3. "조각이 이미 있으면 다시 만들지 않는다"(`pipeline.py:626-631`)는 유지한다 — chunk_id가 바뀌면 임베딩이 CASCADE로 지워진다. 뒤늦게 Ollama가 붙어도 같은 id에 임베딩만 채운다.
4. `chunks_checked` 메타의 뜻은 그대로("임베딩까지 살폈다"). 임베딩을 보류한 실행에서는 세우지 않는다. `app/ui/shell.py:364-368`의 재개 판정은 손대지 않는다(모델 없는 PC에서 열 때마다 재시도하는 현재 동작과 같음. 단 (가)가 매번 0건으로 빨리 끝나는지 확인).
5. `rag.ask`·질문 화면의 "N조각 남음" 안내(`ask.py:423`)가 "임베딩 보류" 상태에서 틀린 문구를 내지 않는지 확인한다.

**시험**

- `test_chunks_stage_is_skipped_without_ollama`의 계약을 **명시적으로 바꾼다**: 조각·조각 FTS는 생기고, 임베딩 0, `chunks_checked` 없음, 보고 문구에 "보류". 이것은 실패 시험을 지우는 것이 아니라 지시서 P0-01-1에 따라 충돌하는 두 계약 중 하나를 택하는 것이며, 변경 사유를 VALIDATION_REPORT에 남긴다.
- 실패한 두 시험은 Ollama를 죽은 주소로 고정해 **개발 PC에서도 CI와 같은 조건**으로 돌린다. 지금은 PC에 Ollama가 있느냐에 따라 결과가 갈린다.
- 신규: 가짜 임베더로 ① 모델 없음 → 조각만 ② 이후 모델 준비 → chunk_id·locator 불변, 임베딩만 추가 ③ 배치 중간 실패 → 다음 실행에서 남은 것만 ④ 모델 교체 → 옛 벡터가 새 모델로 채워지고 조각은 그대로 ⑤ 조각 삽입 도중 중단 → 반쪽 조각 없음(트랜잭션) ⑥ 공식 출처가 문서→조각→인용으로 이어짐(모델 없이).

**변경 파일**: `app/jobs/pipeline.py`, `app/db/repo.py`, `tests/test_chunks_pipeline.py`, `tests/test_onnara_collection.py`, `tests/test_provenance.py`, (문구 확인) `app/ui/views/ask.py`·`app/ui/stages.py`.

### P0-03 질문-근거 불일치 차단

**먼저 할 일 (코드 수정 전)**

- 평가 자료를 `dev`(기존 30·60·24문항) / `regression`(알려진 실패 고정) / `holdout`(신규)으로 나눈다.
- 홀드아웃은 **수정 착수 전에 한 번 작성해 동결**하고(해시 기록), 게이트 판정 때만 돌린다. 결과를 보고 고치면 그 세트는 dev로 내리고 새로 만든다. 작성 주체는 4절의 결정 사항.
- 평가 도구(`app/tools/rag_report.py`)가 정답률·보류 정밀도·보류 재현율·근거 정확성·질문 적합성을 따로 내도록 고치고, 현재 코드로 기준선을 잰다.

**구현 단계 (각각 별도 변경 단위)**

1. `app/search/intent.py` 신설 — 질문을 `대상·속성·기간·범위·의도`로 푸는 규칙 기반 구조(`QueryFrame`). `query.py`의 `QueryScope`(연도·업무 범위)를 품는다. 모델 호출 없음.
2. 속성 사전: 혼동되는 짝을 명시한다 — 계약금액↔정산액, 제출기한↔실제 제출일, 납기일↔준공검사일, 계획↔실적, 예정↔완료, 초안↔승인본, 금액↔비율, 공백↔0. 동의어 묶음마다 **역방향 오답 시험**을 붙인다.
3. `verify.py`에 질문 적합성 검사를 인용 검증과 **별도 단계**로 추가: 인용한 근거가 질문한 대상의 그 속성을 뒷받침하는가. 기존 `_swapped_label`·`_foreign_subject`와 겹치는 부분은 합친다. 탈락 사유는 구조화 코드로 `Answer.generation`에 남기고(본문 없이), 화면에는 일반 안내만.
4. `tablemath.py`: 값 확정 조건을 행·열·문서·연도·단위 동시 일치로 강화. "배정된 예산", "얼마나 썼어" 같은 다른 표현의 과잉 보류는 열 머리글 동의어로 해결하되 2번의 역방향 시험을 통과해야 한다.
5. 충돌 처리: 같은 속성에 서로 다른 값이 승인본/초안, 현행/과거로 갈리면 양쪽 근거를 보이고 보류.
6. 보류 시 "어떤 자료가 있으면 답할 수 있는지"를 속성에서 만들어 안내.
7. 실행마다 답이 갈리는 문제: `app/ai/client.py`의 생성 옵션(temperature·seed)을 확인 — **미확인**. 고정돼 있지 않으면 고정하고, 고정돼 있는데도 갈리면 해당 문항을 규칙 답변 경로로 옮길 수 있는지 본다.
8. 인젝션: `app/ai/prompts/ask.md`에서 문서 구획과 지시 구획의 경계 확인, 문서 속 지시문이 답변·인용 구조를 바꾸지 못하는 회귀 시험 추가.

## 4. 착수 전에 정해야 할 것

1. **git 사용 환경** — 이 세션 셸에 git이 없다. 설치 경로를 알려 주거나, P0-02의 git 명령은 사용자가 직접 실행하는 방식 중 택일.
2. **`.analysis_audit/live-project`의 자료 출처** — 합성인지 실제 자료인지. 실제 자료이고 저장소가 공개라면 P0-02가 P0-01보다 앞선다.
3. **홀드아웃 작성 주체** — 개발 AI가 수정 전에 작성해 동결하는 방식(독립성 약함, 그 한계를 보고서에 명시) 또는 사용자·제3자가 작성하는 방식.
4. **P0-04** — 기관 사양·승인 환경이 없으면 `BLOCKED_EXTERNAL`로 유지.
