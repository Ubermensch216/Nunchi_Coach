## 2. 구조

```text
온나라 2.0 ──(후임자 본인 세션·화면)──> onNara.sAIde
                                          │ ① 사용자가 온나라에서 조회·체크
                                          │ ② 문서별 본문·첨부 다운로드
                                          ▼
              <다운로드>\onNara.sAIde\수집\<실행ID>\  파일들 + package.json   ← "꾸러미"
                                          │                         ▲
                                          ▼                         │ ③ (2차) 브리지: 준비 알림·진행·보유 문서 조회
눈치코치: SaidePackageConnector → Collection(해시·검증·manifest) → 출처 등록 → 노트북·업무 분석
```

지키는 원칙

1. **자료가 지나는 길은 꾸러미 폴더 하나다.** 확장은 스크립트로 내려받는 첨부의 바이트를 읽지 못한다(`chrome.downloads`가 디스크에 쓸 뿐이다). 그래서 파일을 브리지로 올리지 않는다. 폴더는 눈치코치가 꺼져 있어도 만들어지고, 다른 PC로 옮길 수도 있다.
2. **눈치코치에는 연결부 하나만 더한다.** 해시·재개·완전성 판정·출처 등록·노트북 연결은 이미 있는 수집 엔진(`app/jobs/onnara_collect.py`)과 `app/core/provenance.py`, `app/core/onnara_import.py`를 그대로 쓴다.
3. **조회는 사용자가 온나라 화면에서 한다.** sAIde는 화면에 나온 목록과 문서만 다룬다. 전임자 계정·인증서를 쓰지 않고, 확인되지 않은 주소를 추측해 부르지 않는다.
4. **모르는 것은 모른다고 남긴다.** 작성자 ID 없이 이름만 있으면 "이름 기준", 문서 ID 없이 목록 행으로 만든 식별자면 "목록 행 기준", 본문이 화면 글자로 만든 PDF면 "글자 변환본"으로 기록한다. 이런 수집본은 "전체 수집 완료"로 판정하지 않는다.
5. **꾸러미 밖의 파일은 읽지 않는다.** `package.json`이 가리키는 경로는 꾸러미 폴더 안의 상대 경로만 받는다.

검토하고 택하지 않은 길: 눈치코치가 온나라에 직접 접속(인증정보를 앱이 다뤄야 한다) · TONGDAL 경유(원장이 둘이 되고 `.hwp`·`.xlsx`를 색인하지 못한다) · Native Messaging(기관 PC 배포 부담). 공식 API·기록관리 내보내기는 사양을 얻으면 같은 계약(`contract.py`)에 연결부를 더한다.

## 3. 꾸러미 규격 `saide-onnara-package` v1

폴더 하나에 `package.json`과 내려받은 파일이 들어 있다. 글자 부호는 UTF-8.

```json
{
  "format": "saide-onnara-package",
  "version": 1,
  "run_id": "20261012_153000_4f2a",
  "created_at": "2026-10-12T06:30:00.000Z",
  "exporter": { "name": "onNara.sAIde", "version": "0.9.0" },
  "system": { "origin": "http://onnara.example.go.kr", "institution": "" },
  "scope": {
    "kind": "selection",
    "list_name": "기록물등록대장",
    "author_ids": [], "author_names": [],
    "start_date": null, "end_date": null, "departments": []
  },
  "listing": { "total": null, "finished": false },
  "documents": [
    {
      "document_id": "row-3f9c…",
      "id_basis": "list-row",
      "title": "2025년 실적 보고",
      "document_number": "",
      "author_id": "", "author_name": "홍길동", "department": "기획과",
      "authored_at": "2025-09-01",
      "status": "",
      "assets": [
        { "asset_id": "a1", "role": "body", "filename": "2025년 실적 보고_본문.pdf",
          "path": "20250901_2025년 실적 보고/2025년 실적 보고_본문.pdf",
          "status": "complete", "fidelity": "rendered-text" },
        { "asset_id": "a2", "role": "attachment", "filename": "붙임1.hwpx",
          "path": "20250901_2025년 실적 보고/붙임1.hwpx",
          "status": "complete", "fidelity": "original" },
        { "asset_id": "a3", "role": "attachment", "filename": "붙임2.xlsx",
          "status": "failed", "message": "다운로드가 중단되었습니다." }
      ]
    }
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `run_id` | 실행 ID이자 꾸러미 폴더 이름. 영숫자·밑줄·붙임표만 쓴다. 눈치코치는 이 값으로 수집본 폴더(`<프로젝트>/onnara/<run_id>/`)를 정한다 |
| `scope.kind` | `selection` 사용자가 체크한 문서 · `listing` 조회한 목록 전체(S5) |
| `scope.author_ids`/`author_names` | `selection`에서는 비운다(체크한 문서가 곧 범위다 — 작성자를 선언하면 보고자 칸이 빈 문서가 범위 밖으로 빠진다). `listing`에서 조회 조건으로 준 작성자를 적는다 |
| `listing.total`/`finished` | 화면이 밝힌 전체 건수와 끝까지 돌았는지. `listing`이고 작성자 ID가 있을 때만 완전성 판정에 쓴다 |
| `id_basis` | `source-document-id` 온나라 문서 ID · `management-number-and-date` 관리번호+일자 · `list-row` 목록 행(제목·일자·부서·보고자)의 해시 |
| `authored_at` | 목록의 보고·시행·접수 일자. `YYYY-MM-DD`가 아니어도 눈치코치가 흔한 표기(`2025. 9. 1.`, `20250901`)는 읽는다 |
| `assets[].path` | **꾸러미 폴더 기준 상대 경로**(`/` 구분). 절대 경로와 `..`는 거절한다 |
| `assets[].status` | `complete`만 가져온다. 나머지는 "받지 못한 파일"로 남는다 |
| `assets[].fidelity` | `original` 온나라가 준 파일 그대로 · `rendered-text` 화면 글자로 만든 PDF · `extracted-text` 추출 글자(`.md`) |
| `assets[].truncated` | (선택) `true`면 확장이 본문을 끝까지 읽지 못했다. 받은 파일(`complete`)이지만 본문 전체가 아니다. 눈치코치는 수집본의 `package.body_truncated`에 건수를 남기고 가져오기 전 안내에 밝힌다 |

**공통 계약 파일.** `tests/fixtures/saide_package_v1.json`(눈치코치)과 `src/lib/nunchi/package.fixture.json`(sAIde)은 같은 파일이다. sAIde는 꾸러미 작성기가 정확히 이 내용을 만드는지, 눈치코치는 이 내용을 읽어 수집하는지 시험한다. 규격을 바꾸면 두 파일과 이 절을 함께 바꾼다.

눈치코치가 읽을 때의 규칙(`SaidePackageConnector`)

- 연결부 표시: `adapter="saide-package-v1"`, `system_id="onnara@<호스트>"`, 기관명이 비면 호스트를 쓴다. `simulation=False`, `live_verified=False`(V1 전까지).
- 작성자: `author_id`가 없으면 `name:<이름>`을 식별자로 쓰고 수집본에 `author_identity="name"`을 남긴다. 동명이인을 가를 수 없으므로 `authoritative_total=False` → 완전성은 `unknown`.
- 범위: 꾸러미가 기간을 밝히지 않으면 문서 일자의 최소·최대를 쓴다. 일자를 읽지 못한 문서는 범위 밖으로 기록된다(수집 엔진의 `listing_errors`).
- 본문 역할의 파일이 없는 문서는 수집 엔진이 `metadata_errors`로 남기고 수집본은 `partial`이 된다.
- 수집본 폴더는 꾸러미 폴더 안이나 그 위에 둘 수 없다(원본 보호 — 엔진의 `protected_roots`).

## 6. 브리지(2차) 설계 요약

- 눈치코치가 `127.0.0.1:<고정 포트>`에 `http.server` 기반 서버를 연다. 포트는 TONGDAL(47821)과 겹치지 않게 한다(가칭 47831). 기본은 꺼짐.
- 보안 규칙은 TONGDAL 브리지와 같다: Host 헤더 검사, `Origin`은 등록된 `chrome-extension://<ID>`만, CORS 응답 헤더 없음, 6자리·5분·1회용 연결 코드, 토큰은 SHA-256만 저장, 상수 시간 비교, 실패 반복 시 일시 차단.
- 구현된 계약(B1·B2, B3가 맞출 것): 기본 주소 `http://127.0.0.1:47831`. `GET /bridge/v1/status` → `{app:"nunchi-coach", apiVersion:1, appVersion, paired}`(+연결됐으면 `scopes`, `project`). `POST /bridge/v1/pair {code, label}`(확장 Origin 필수, 토큰 없이) → `{token, clientId, scopes:["read"], apiVersion}`. 그 뒤 요청은 `Authorization: Bearer <token>`. 오류는 `{code, message}`이고 `message`는 사용자에게 보여도 되는 한글이다. 연결 오류 코드: `pairing_not_started`(409) · `pairing_code_mismatch`(403) · `pairing_code_expired`(410) · `pairing_code_exhausted`(429) · `origin_required`(403). 공통: `unauthorized`(401) · `origin_mismatch`·`scope_denied`·`host_rejected`·`origin_rejected`(403) · `rate_limited`(429).
- TONGDAL과 다른 점: 연결할 때 눈치코치 쪽 허용 확인 창이 없다(코드를 만든 것이 곧 허용이다). 그래서 `pair`는 곧바로 답한다 — 확장이 2분 넘게 기다릴 필요가 없다.
- 구현된 계약(B4): `POST /bridge/v1/packages {runId, path}`(권한 `write`) → 202 `{runId, state, documents, files, project}`. `path`는 꾸러미 폴더의 절대 경로이고, 수신 폴더(다운로드 폴더 + 설정에서 더한 폴더) 아래의 `…/onNara.sAIde/수집/<runId>` 모양이며 그 안의 `package.json`이 같은 실행 ID를 밝혀야 한다. 거절: `invalid_request`(400) · `path_rejected`(403) · `package_unreadable`(422). `state`는 `queued`(물을 차례) · `asked`(묻는 중) · `imported` · `dismissed` · `failed`. `GET /bridge/v1/packages/{runId}`(권한 `read`) → 같은 상태. `POST /bridge/v1/known {origin, ids(≤500)}`(권한 `read`) → `{known: [...], project}` — 열어 둔 인수인계가 본문을 받았고 받지 못한 파일이 없는 문서만. 인수인계를 열지 않았으면 `no_project`(409). 연결할 때 주는 권한은 `read`·`write`다.
- 엔드포인트(v1): `GET /bridge/v1/status` · `POST /bridge/v1/pair` · `POST /bridge/v1/packages`(꾸러미 폴더 경로 통지 — **허용한 수신 폴더 아래일 때만** 받는다) · `GET /bridge/v1/packages/{runId}`(진행·결과) · `POST /bridge/v1/known`(문서 식별자 목록 → 이미 가진 것).
- 브리지가 꺼져 있어도 꾸러미는 만들어진다. sAIde는 "눈치코치에서 폴더를 직접 고르세요"로 안내한다(fail-closed가 아니라 수동 경로로 떨어진다 — 자료 경로가 브리지에 의존하지 않기 때문).

- 연결 권한을 `read`·`write`로 늘렸다(7차에서는 `read`뿐). 이미 맺은 연결에는 저절로 붙지 않으므로, B2 상태에서 연결해 둔 확장은 알림 때 "알림 권한이 없습니다. 다시 연결하세요"가 나온다.
- "이미 가진 문서"를 **받지 않는 것을 기본 동작**으로 했다(계획은 조회까지만 적혀 있었다). 묻지 못하면(연결 없음·꺼짐·오류) 아무것도 빼지 않는다. 같은 날 같은 제목의 문서가 둘 이상 골라졌으면 그 문서들도 빼지 않는다 — 목록 행 식별자로는 둘을 가를 수 없다.
- 알림을 받았다고 자동으로 가져오지 않는다. 눈치코치 창에서 사용자가 승인해야 등록된다.
- §6에 있던 "수신 폴더"를 다운로드 폴더(운영체제에 물은 위치) + 설정에서 더한 폴더로 정했다. Edge의 다운로드 위치를 따로 바꿔 둔 PC는 그 폴더를 한 번 더해야 알림이 받아진다(안 더해도 폴더를 직접 고르면 된다).

**확인하지 못한 것**

- 실제 눈치코치 창에서 등록 확인 창이 뜨는 모습과 시점(시험은 확인 창을 대역으로 바꿔 돌렸다). 다른 대화상자가 떠 있는 동안 알림이 오면 어떻게 보이는지도 보지 않았다.
- 실제 Edge에서 내보내기 → 알림. 8차의 Origin 전제가 그대로 걸려 있다.
- 실제 PC의 다운로드 폴더 위치 판정(시험은 수신 폴더를 임시 폴더로 지정했다. 윈도우에 묻는 함수가 절대 경로를 돌려주는 것까지만 확인).
- 분석이 도는 중(프로젝트 DB에 쓰는 중)에 보유 문서 조회가 겹칠 때. 읽기 전용 연결에 5초 제한을 두었고 실패하면 `project_busy`로 답하지만, 실제로 겹쳐 보지는 않았다. sAIde는 조회에 실패하면 아무것도 빼지 않고 진행한다.
- "이미 가진 문서"는 목록 행 식별자(제목·일자·부서·보고자) 기준이다. 온나라에서 제목이나 보고자가 바뀌면 새 문서로 보고, 반대로 내용만 바뀐 문서는 가진 것으로 본다. 문서 ID를 읽게 되면(S4) 다시 볼 것.
