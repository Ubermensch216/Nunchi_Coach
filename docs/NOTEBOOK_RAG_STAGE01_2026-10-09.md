# 노트북 RAG 1차 구현·검증 기록

기준 계획: [노트북 RAG 고도화 계획](NOTEBOOK_RAG_UPGRADE_PLAN_2026-10-09.md). 단계 0의 평가·검색 진단과 단계 1의 범위·인원 역할 검증을 구현했다. 단계 2의 두 글자 용어 검색도 작은 수정으로 함께 보완했다.

## 구현한 동작

- 업무·연도를 벡터/글자 검색의 후보 개수 제한 전에 적용한다. 선택 범위를 먼저 적용한 뒤 중복을 제거해 다른 연도의 동일 본문이 요청한 연도의 근거까지 제거하지 않게 했다.
- `QueryScope.predicate`에 문서 범위·업무·연도·원문 존재 조건을 모았다. 질문 대상 존재 검사와 질의어 빈도, 이웃 확장도 같은 범위를 사용한다. 선택하지 않은 문서의 추가/삭제가 보조 판정에 영향을 주지 않게 했다.
- `예산` 같은 두 글자 핵심어는 trigram이 처리하지 못하면 범위 안에서 정확 문자열로 찾는다. 조사 하나가 붙은 세 글자 형태도 지원한다. 모든 한국어 표현 차이를 해결하는 형태소 색인은 아니다.
- ‘담당 인원’, ‘참석 인원’처럼 명시적 역할을 묻는 사람 수는 역할·숫자가 같은 원문 문장/표 항목에 묶여 있어야 답한다. 다른 문서의 업무명이나 다른 문장의 역할을 빌려 숫자를 승인하지 않는다. 옳은 수량 문장과 틀린 추가 문장이 함께 생성되면 확인된 문장만 남긴다.
- 표에서 코드로 읽은 값은 기존 무단위 표 답변을 보존하면서 인원 역할을 다시 확인한다. 의미 색인과 질의 벡터의 차원이 다르면 예외로 종료하지 않고 검색 결과와 재색인 안내를 제공한다.

대상 파일: `app/search/query.py`, `rag.py`, `fts.py`, `quantity.py`, `app/core/notebook.py`.

## 검색 진단

`app/search/trace.py`의 검색 기록을 답변의 `generation.retrieval`에 붙인다. DB 스키마 변경 없이 기존 노트북 답변 JSON에 저장한다.

- 확장·임베딩·행렬 적재·의미 검색·글자 검색·선별·문맥 구성·생성·검증 시간.
- 후보/선택/문맥 개수, 범위·탐색 제한·중복·다양성으로 제외한 개수, 변형 질의의 신규 후보 수, 생성 호출·폐기 문장 수.
- 선택 조각/문서 ID, 문맥 글자 수, 검색·직접 항목 대조·검색 대체 경로, 보류 원인.
- `generation.notebook_trace`에는 자료 수·직전 질문 수·후속 질문 독립화 여부·스냅샷/독립화/질문 처리 시간을 남긴다.

검색 진단에는 질문·파일명·원문 발췌를 넣지 않는다. 일반 대화 이력과 인용 원문 저장은 기존 기능이다. 이 둘과 평가 CLI의 원시 답변 저장을 운영 진단과 혼동하지 않는다. 이 단계에서는 별도 관리자 UI나 외부 로그 전송을 추가하지 않았다.

## 동결 평가와 재현

`app/tools/notebook_eval.py`는 `notebook.query`를 직접 실행한다. 선택 변경·후속 질문·전체 정리·저장된 답변·SHA-256 판본·원문 인용을 함께 검증한다. 모델이 없는 검색 대체 결과를 올바른 보류로 채점하지 않는다. 기존 프로젝트를 평가용으로 초기화하거나 기존 결과 파일을 덮어쓰지 않는다.

평가 자료는 [개발 60개](../tests/fixtures/notebook_rag_2026_10_09/dev.json)와 [예약 최종 60개](../tests/fixtures/notebook_rag_2026_10_09/holdout.json) 시나리오다. 각 세트는 12개 유형을 별도 업무 5개에 적용한다. 각 세트의 원문은 30건, 대화 차례는 75개다. 업무·파일·수량/금액을 분리하고 코드 수정 전에 [SHA-256 원장](../tests/fixtures/notebook_rag_2026_10_09/frozen_manifest.json)을 기록했다.

문항과 정답을 개발 주체가 직접 작성한 합성 자료이며 독립 작성자·기관 실자료 평가는 아니다. 최종 세트의 결과로 다음 코드를 조정한다면 그 세트는 개발용으로 전환하고 새 최종 자료를 먼저 동결해야 한다.

기준 코드는 `.test_runs/notebook-rag-baseline-20261009/`에 보존했다. 분석 중 공유 저장소의 HEAD가 `d95d3bf`에서 `c31e53a`로 변경됐으므로 Git 커밋만으로 실행 상태를 판단하지 않는다. 평가 결과는 실제 파일 해시·모델 digest·씨앗·선택 스냅샷을 기록하며, 기준선은 보존한 코드에서 실행했다.

```powershell
# 전체 세트를 측정할 때는 --limit을 생략한다. 첫 비교는 --limit 12로 유형별 1개씩 측정했다.
.\.venv\Scripts\python.exe -m app.tools.notebook_eval --suite dev --phase candidate --folder .test_runs/notebook-dev-new --json .test_runs/notebook-dev-new.json --limit 12 --repeat 3 --expansion both

# 최종 결과는 개발 조정에 사용하지 않는다.
.\.venv\Scripts\python.exe -m app.tools.notebook_eval --suite holdout --phase candidate --folder .test_runs/notebook-final-new --json .test_runs/notebook-final-new.json --repeat 3 --expansion off
```

CLI 결과의 `partial`은 전체 시나리오 실행 여부다. `complete`는 요청한 실행이 끝났는지만 나타내며 부분 실행도 완료되면 True가 된다. 이를 전체 세트 통과로 표현하지 않는다.

## 현재 검증 범위

수정 전 신규 회귀 10개 중 7개 실패·3개 통과를 확인했다. 후보 누락·범위 보조 판정·인원 역할·검색 진단을 포함한다. 이후 양성 수량·제로·표 머리글·복수 인용·추가 오답 문장·두 글자 검색·벡터 차원 오류 사례를 확장했다.

첫 실제 모델 비교는 개발 세트의 앞 12개 유형/15개 대화 차례를 씨앗 0·1·2와 질문 확장 off/on으로 측정했다. 기준선은 매회 10/12 시나리오·13/15 차례 통과했다. 선택 자료에 답이 없는 경우와 선택 변경 후 후속 질문에서 근거 없는 확정이 반복됐다. 중간 후보 구현은 매회 12/12·15/15로 개선됐지만 이후 문장별 역할 검증과 진단을 보강했으므로 그 결과를 최종 코드의 성적으로 쓰지 않는다.

최종 코드의 개발 재측정은 매회 **12/12 시나리오·15/15 대화 차례 통과**였다. 확장 off/on과 씨앗 0·1·2의 여섯 조합에서 동일하다. 각 조합의 답할 차례 11개는 기준선과 후보 모두 통과했고, 필요한 보류 4개는 기준선 2/4에서 후보 4/4로 바뀌었다. 전체 개발 60개 중 12개를 실행한 결과이며 전체 개발 세트의 성적으로 표시하지 않는다.

| 검증 | 결과 |
|---|---|
| 최종 개발 반복 비교 | 기준선 매회 10/12 → 후보 매회 12/12. 15개 대화 차례 중 13/15 → 15/15 |
| 예약 최종 평가 | 확장 off, 씨앗 0·1·2에서 **매회 60/60 시나리오·75/75 차례 통과**. 3회 합계 180/180·225/225 |
| 신규 평가 도구·범위·역할·기존 생성/수량 집중 시험 | 87개 통과 |
| 최종 전체 회귀 | `NUNCHICOACH_LIVE_AI=1 pytest -q -rs` **1,491개 통과·1개 건너뜀·경고 1개**, 677.78초 |
| Windows PyInstaller 빌드 | 통과. `app.search.trace`, `quantity`, `query`, `rag`가 실행 파일 PYZ에 포함됨을 확인 |
| 번들 자체 점검 | 합성 표본 81건 파싱 및 업무 복원→수행 기록→복원본→묶음→가져오기→재연결 통과 |
| 의존성 잠금·공백 검사 | 잠금 환경 일치, `git diff --check` 통과 |
| 저장소 추적 검사 | 기존 `.analysis_audit` 추적 파일 1,981개로 실패. 기능 회귀 통과를 전체 CI 합격으로 표시하지 않음 |

전체 회귀에서 건너뛴 것은 실제 기관 문서 표본 미제공 검사이며, 경고는 기존 Qt 마우스 이벤트 생성자의 폐기 예정 안내다. 번들 파싱 표본에는 HWP가 없어 그 형식의 실물 검증으로 해석하지 않는다. 다른 PC나 원격 CI에서의 검증도 아니다.

예약 최종 세트는 5개 별도 업무의 60개 시나리오를 전부 실행했다(`partial=False`). 각 회차에서 답할 수 있는 55개 차례와 필요한 보류 20개 차례가 모두 통과했고, 근거 없는 확정·저장된 범위/판본/원문 인용 불일치는 0건이었다. 결과를 본 뒤 제품 코드·동결 자료·채점 조건을 수정하지 않았고 실행 종료 시 코드 해시 일치를 확인했다.

이 평가는 확장 **off** 경로의 전체 최종 평가다. 확장 on은 앞선 개발 12개 시나리오에서만 3회 비교했으며, 최종 60개 전체의 on 경로를 검증했다고 표시하지 않는다. 같은 75개 차례를 세 번 실행한 것이지 서로 다른 225개 독립 문항은 아니다. 산문·전체 정리의 주장 의미를 사람이 전수 검토한 결과도 아니며, 합성 세트 통과로 실제 기관 자료의 정답률 100%를 선언하지 않는다.

정확도와 지연을 구분한다. 개발 장비에서 회귀·빌드와 모델 평가를 함께 실행한 시간은 전용 성능 벤치마크로 사용하지 않는다.

로컬 실행 증거:

- `.test_runs/notebook-eval-baseline-frozen.json`: 보존한 코드의 기준선, 부분 개발 세트.
- `.test_runs/notebook-eval-candidate-final.json`: 최종 코드의 확장 off/on 개발 비교. 종료 후 코드 해시 일치 확인.
- `.test_runs/notebook-eval-holdout-final.json`: 전체 예약 최종 세트의 확장 off 반복 평가.
- `.test_runs/notebook-rag-full-final-v2.txt`: 최종 전체 회귀.
- `.test_runs/notebook-rag-bundle-build.txt`, `notebook-rag-bundle-selftest.txt`: 빌드·번들 자체 점검.
- `.test_runs/notebook-rag-bundle/NunchiCoach/`: 이번 검증 실행물. 원문과 분석 프로젝트를 포함하지 않는다.

## 남은 계획

- 명시적 인원 역할에 한정한 규칙 검증이다. 일반 산문의 의미 충돌·복잡한 비교·동의어 역할·효력 판정은 완료로 표시하지 않는다. 불확실한 관계를 확인할 수 없으면 보류할 수 있다.
- 신규 개발 세트 전체의 반복 비교, 실제 기관 자료와 별도 검토자의 정답, 상대연도 기준일을 주입하는 노트북 평가가 남아 있다. 현재 동결 시나리오는 절대연도를 사용한다.
- 부모·자식 청킹, 표 구조의 파서 공통 계약과 재색인 전환, 확장 질의 의미 보존, 전체 정리 커버리지·캐시는 다음 단계다.
- 재정렬 모델·Qdrant·그래프 보강은 효과와 실행 비용을 측정한 뒤 채택한다.

다음 착수점은 [계획 단계 2](NOTEBOOK_RAG_UPGRADE_PLAN_2026-10-09.md)의 구조 보존 청킹이다. 기존 대화의 `chunk_id`·locator·저장 발췌를 보존하는 색인 버전 전환과 표의 머리글/단위 계약을 함께 설계해야 한다.
