## 2. myAI ‘정보탐색’의 실제 RAG

`public/index.html:37`의 ‘정보탐색’은 `chat` 뷰다. 단일 RAG 엔진 메뉴가 아니라 첨부 파일, 부서 지식팩, 전체 문서 분석 등의 경로를 공유하는 대화 화면이다.

### 2.1 개인 첨부와 부서 지식팩은 다르다

| 경로 | 동작 | 의미 |
|---|---|---|
| 개인 첨부 | `ollama.js:1094`의 `buildContext`: 자료가 문맥 예산 이내면 전부 사용. 초과하면 질문 확장 → 질문·첨부 조각 임베딩 → 메모리 BM25/벡터 검색 → RRF | 작은 자료는 검색 자체를 생략한다. 큰 첨부는 해당 호출에서 조각 임베딩도 요청하므로 비용 측정이 필요 |
| 부서 지식팩 | `departmentRag.js:27`의 `searchNotebook`: 사전 색인 자료에서 확장 질의 → 의미/글자 검색 → 선택형 그래프 보강 → RRF → 선택형 rerank → 부모 문맥 복원 → 예산에 맞게 선택 | 영속 색인, 장애 시 대체 검색, 진단/관리 기능이 중심 |
| 정밀 분석 | `mapReduce.js`: 조각 묶음별 분석과 최종 종합 | 질의별 Top-K 검색과 별도. 기본 최대 80조각이며 초과분은 앞에서 제한하므로 완전한 전수 분석으로 해석하면 안 됨 |

부서 검색의 코드 기본값은 **JSON 벡터 + 메모리 검색**이다. Qdrant + SQLite는 지원하는 배포 프로필이며 컨테이너 설정 예시는 이를 사용한다. 해당 기능이 코드에 있다는 이유로 모든 설치가 Qdrant를 사용한다고 판단하면 안 된다.

### 2.2 참고할 구현

1. **부모·자식 청킹.** 지식팩 수집은 `hierarchical: true`를 사용한다. 기본 부모 목표 1,024자/겹침 256자, 자식 256자/겹침 64자다. 자식으로 세밀하게 검색한 뒤 부모의 문맥을 복원하고 같은 부모는 한 번만 넣는다. Markdown 표 블록을 부모에서 유지한다. 이 크기는 목표값이며 긴 블록이나 표가 반드시 그 길이 이하라는 뜻은 아니다.
2. **한국어 짧은 낱말 검색.** 원래 단어에 CJK bigram을 더해 BM25와 SQLite 검색에 사용한다. ‘예산’, ‘계약’처럼 짧은 업무 용어의 재현율을 보완할 수 있다.
3. **다중 질의 + RRF.** 원질문과 최대 3개 변형을 검색한다. 확장 실패/시간 초과 시 원질문으로 진행한다. 확장 기본 제한 시간은 6초다.
4. **색인 운영과 진단.** Qdrant/SQLite 이중 기록, 수집 작업 재시도·재개, 색인 점검/재구축, 검색 단계별 시간과 대체 경로 사유를 기록한다. 검색 로그는 원질문 대신 해시·길이를 남긴다.
5. **선택형 그래프 보강.** 질문과 맞는 엔터티/별칭에서 1-hop 관계를 따라 원문 조각을 추가한다. 일반적인 무제한 다단 추론이 아니다. `KG_EXPANSION_ENABLED=1`일 때 작동하고 코드 기본은 꺼짐이다.

### 2.3 그대로 가져오면 안 되는 부분

- **재정렬 모델은 기본 꺼짐이다.** `reranker.js`에 `bge-reranker-v2-m3`와 `/api/rerank` 호출이 있지만, 이 코드의 존재만으로 작동하는 cross-encoder가 배포됐다고 볼 수 없다. 별도 런타임/API 호환성과 실제 호출 성공을 확인해야 한다. 실패하면 원순위로 돌아간다.
- **일반 노트북 답변은 근거 사용·보류를 주로 프롬프트에 요구한다.** 검토한 일반 RAG 경로에서는 Nunchi의 숫자·단위·속성에 대한 문장별 후처리와 동등한 검증을 확인하지 못했다. 법령 전용 검증을 일반 노트북 검증으로 간주하지 않는다.
- **검색 실패 시 자료 일부를 문맥으로 넣는 대체 경로가 있다.** `departmentRag.js` 및 `retrieval.js`의 `greedyFit` 대체 처리를 Nunchi에 이식하면, 관련 근거 없음과 검색 서비스 장애를 혼동할 수 있다. Nunchi의 보류 정책을 유지해야 한다.
- **평가기도 그대로 복사하지 않는다.** `computeCaseMetrics`는 문서 단위 정답에서 같은 문서의 여러 조각을 각각 적중으로 센다. 이번 진단에서 정답 문서 1개·반환 조각 2개를 넣자 `recall=2`가 반환됐다. 문서 Recall은 문서 ID를 중복 제거해야 한다. 자식 검색과 부모 복원 이후의 정답 단위도 일치시켜야 한다.
- **GraphRAG나 큰 문맥 자체는 정답률 보장이 아니다.** 부정확한 엔터티 연결·질의 확장이 잘못된 업무의 근거를 늘릴 수 있다. 같은 평가셋의 기능별 비교가 선행돼야 한다.

## 3. Nunchi_Coach 현재 수준

### 3.1 실제 노트북 경로

```text
선택 자료·허용 상태·파일 SHA-256 스냅샷
  → 동일 자료 선택에서의 최근 질문 최대 3개로 후속 질문 독립화
  → 일반 질문 / 전체 정리 라우팅
  → 명시적 항목 직접 인용·상충 판정 또는 검색
  → 원질문 + 최대 3개 확장 질의
  → NumPy 의미 검색 + SQLite FTS5 → 가중 RRF
  → 후보 제한·중복 정리·업무/연도 필터·규칙 재정렬
  → Top-8 + 관련 이웃 확장 + 질문 관련 대목 선택
  → 규칙 계산 또는 JSON 구조의 답변 생성
  → 문장별 숫자·단위·표 칸·속성·주제 검사
  → 현재 선택·판본 재확인 → 인용 원문과 답변 저장
```

AI 답변을 다시 원문 근거로 쓰지 않고 앞선 **질문**만 후속 검색에 이용한다. 실제 파일 해시와 선택 범위를 질문 전후에 점검하는 것은 유지할 장점이다. 핵심 연결은 `app/core/notebook.py`의 `query`다.

| 영역 | myAI | Nunchi_Coach 현재 | 판단 |
|---|---|---|---|
| 기본 검색 | BM25/벡터/RRF, JSON 또는 Qdrant·SQLite | NumPy/FTS5/RRF | 하이브리드 검색을 새로 도입할 필요 없음 |

| P0 | 보조 판정이 노트북 범위를 공유하지 않음 | `_subject_unknown`은 전체 DB를 조회. 선택하지 않은 문서를 추가했을 때 같은 질문의 대상 부재 판정이 True→False로 바뀜. 이는 **보조 판정의 범위 의존성 재현**이며 범위 밖 인용 유출을 재현했다는 뜻은 아님. `_distinctive_terms`의 전역 통계도 함께 검토 |
| P0 | 대상·역할을 바꿔 붙인 수량 답변 | 기존 최종 평가에서 3회 동일 실패. 이름표 없는 산문과 표에서의 일반 의미 검증 부족 |
| P1 | 두 글자 업무 용어의 글자 검색 누락 | `fts.search_chunk_ids('예산')`: 해당 단어 포함 17조각인데 0개 반환. 의미 검색이나 search-only의 LIKE 대체가 보완할 수 있으므로 전체 RAG가 반드시 실패한다는 뜻은 아님 |
| P1 | 구조 없는 강제 분할 | `chunking.py:50`에서 1,200자마다 절단. 길어진 표의 제목·머리글·단위·행 관계가 분리될 가능성. 일반적인 부모/자식 및 원문 범위 정보 없음 |
| P1 | 확장의 효과·의미 보존 미검증 | 현재 확장 출력은 길이·중복을 정리하지만 대상/연도/숫자 변경을 구조적으로 검사하지 않음. 세 변형의 누적 가중치 때문에 0.5 가중치가 원질문 우선순위를 항상 보장하지는 않음 |
| P1 | 전체 정리의 커버리지 한계 | `overview.py`: 48조각 표집, 최대 60개 사실 도달 시 map 루프 중단. 최종 문장 최대 10개. 모든 선택 자료를 검토한 것으로 받아들이지 않도록 실제 처리 커버리지 필요 |
| P2 | 색인 프로필·규모 관리 | 임베딩 모델 이름과 차원을 사용하지만 현재 `_load_chunk_matrix`는 첫 행의 차원과 같은 행만 사용. 질의 벡터와의 차원 불일치·같은 모델 태그의 내용 변경에 대한 명시적 관리 필요 |

`MIN_SIMILARITY=0.40`은 작은 합성 평가로 정한 값이며 답할 질문/보류할 질문의 점수 분포가 겹친다. 이 값이나 FTS 상위 순위를 사실 신뢰도로 표현해서는 안 된다.

이번 진단은 제품 DB를 열지 않고 임시 DB에서 수행했다. 재현 스크립트/결과는 로컬 `.test_runs/rag_plan_probe_20261009.py`와 같은 이름의 JSON에 보관했다. 회귀 통과와 이런 미포함 사례의 실패는 양립한다. 분석 중에도 공유 작업 트리의 다른 변경이 진행됐으므로 시험 결과는 실행 시점의 결과다. 마지막 확인에서 핵심 범위·후보 선별 구조가 유지됨을 다시 읽었으며, 후속 구현 전 기준 코드를 별도로 고정해야 한다.

## 5. 목표 구조

```text
질문 + 선택 자료/판본
  → 공통 검색 범위 계약
  → 의도·대상·역할·속성·기간 추출
  → 원질문 우선 검색 / 필요할 때만 통제된 확장
  → 범위 내 후보 검색: 벡터 + 한국어 글자 검색 + 정확 식별자
  → RRF → 후보 적합성 검사 → 규칙 또는 선택형 cross-encoder
  → 부모 문맥/표 머리글 복원 + 문맥 예산
  → 원문에 연결된 근거 묶음
  → 직접 조회 / 계산 / 비교 / 전체 정리 / 생성
  → 문장별 근거 연결·질문 적합성·상충 검증
  → 답변 / 부분 답변 / 보류 / 자료 준비 상태
```

핵심 계약은 두 가지다.

- **검색 범위:** `doc_ids`, 사용자 선택, 허용 여부, 버전 해시, 문서 존재/파싱 상태, 업무/기간을 하나의 객체로 고정한다. 검색·직접 항목 대조·이웃/부모 확장·보조 판정·생성 검증·UI가 동일 계약을 사용한다. 연도는 문서 작성연도와 사실의 적용기간을 구분하며, 연도 미상/다년도 문서를 무조건 현재 연도에 편입하지 않는다.
- **근거 묶음:** 원문 문서/판본, child/parent ID, 원문 locator/범위, 원문 발췌, 검색 점수와 검증 상태를 분리한다. 검색용으로 제목·업무명을 덧붙이더라도 그 문자열을 원문 직접 인용으로 저장하지 않는다. 모든 검색 점수는 순위 신호이며 사실의 진실 확률이 아니다.

## 6. 단계별 실행 계획

기간은 개발자 1명과 현재 구조를 전제로 한 작업량 추정이다. 모델 평가 대기, 실제 기관 자료 준비, Windows 런타임 호환성에 따라 달라진다. P0→P1은 필수 기반이고, 모델/그래프/검색 서버 도입은 별도 채택 기준을 통과할 때 진행한다.

### 단계 0 — 노트북 평가 기준선과 검색 추적 (2~3일)

- `notebook.query`를 직접 실행하는 평가 도구를 만든다. 기존 `rag_report`/`rag_quality`의 `ask` 중심 평가와 구분한다. 자료 선택 변경, 후속 질문, 자동 전체 정리, 인용 저장까지 시험한다.
- 현재 작업 트리 코드 해시, 모델 digest/설정, parser/chunker 버전, 원문 해시, 선택 스냅샷, 질문 시각을 고정한다. 상대연도 시험은 기준 날짜를 명시한다.
- 신규 개발/최종 세트를 업무·문서 단위로 분리한다. 120~200개 문항/대화 시나리오를 시작 규모로 삼되 정답·보류·범위 변경·다른 업무의 같은 숫자·상충·표·2글자 용어·동의어·전체 정리를 균형 있게 포함한다. 가능한 실제 익명화 자료와 별도 검토자 정답을 추가한다.
- 확장/검색/필터/문맥 구성/생성/검증 시간, 각 단계 후보 수, 제거 사유, 원질문 대비 변형 후보 기여도를 기록한다. 기본 운영 로그에는 본문을 넣지 않는다. 디버그 원문은 별도의 로컬 평가 모드에서만 보관한다.
- 기준선은 확장 off/on을 같은 자료·질문·모델로 비교하고 생성 경로는 씨앗을 바꾸어 3회 이상 실행한다. 이미 결과를 보고 개발에 사용한 세트를 새 최종 세트로 재사용하지 않는다.

대상: `app/tools/`의 신규 노트북 평가 도구, `app/search/rag.py`, `expand.py`, `overview.py`, `app/core/notebook.py`.

완료 기준: 오답을 검색 누락·잘못된 후보 채택·생성 오류·검증 과잉 보류·범위 오류로 분류할 수 있고 실행 조건으로 재현할 수 있음.

### 단계 1 — 범위와 답변 적합성 수정 (3~5일, P0)

- 업무/기간을 가능한 한 후보 검색 전에 적용한다. 이후 후보 수를 제한하되 약한 근거를 무제한으로 채우지 않는다. 현재 16개 제한이 막던 무관 자료 승격 회귀를 함께 유지한다.
- `_subject_unknown`, `_distinctive_terms`, 직접 항목·이웃·표 처리 등 전체 DB 보조 조회에 공통 범위를 적용한다. 선택하지 않은 자료의 추가/삭제가 같은 노트북의 판정에 영향을 주지 않는지 시험한다.
- 질문과 근거에 `대상 업무 / 역할 / 속성 / 기간 / 값 / 단위`를 연결한다. ‘담당 인원’과 ‘방문 인원’, ‘계획’과 ‘실적’, ‘제출기한’과 ‘실제 제출일’을 별개로 검증한다. 처음에는 명시적인 연결을 우선하고 불확실한 일반 산문은 부분 답변·보류로 처리한다.
- 같은 이름표에 한정된 상충 검사를 점진적으로 확장한다. 파일명의 ‘최종’과 수정 시각은 법적·업무상 효력 판정으로 사용하지 않는다.
- 보류 사유를 ‘일치 근거 없음 / 상충 / 판본 변경 / 의미 색인 미완료 / 생성 실패’로 구분한다. 검색 서비스 장애를 자료 부재로 표현하지 않는다.

대상: `rag.py`, `query.py`, `facts.py`, `intent.py`, `quantity.py`, `verify.py`, 노트북 대화/근거 UI.

완료 기준: 이번 범위·후보 누락 진단 해결, 기존 수량 실패를 포함한 새 업무/역할 대조군 통과, 선택 범위 밖 인용 0건, 정답이 있는 양성 문항의 과잉 보류 악화 없음.

### 단계 2 — 구조 보존 청킹과 한국어 검색 (4~6일, P1)

- 파서 출력에 제목 계층, 페이지/문단, 표 ID, 머리글, 행/셀 범위, 단위, OCR 여부를 보존한다. XLSX의 기존 행·셀 정보를 재사용하고 DOCX/HWPX/PDF는 추출 가능 수준별로 확장한다.
- 자식은 정확한 대목 검색에, 부모는 이해할 문맥 복원에 사용한다. 산문은 문장/문단 경계로 나누고 표는 머리글·단위를 가진 행 묶음으로 나눈다. 긴 표 전체를 무조건 한 부모로 만들지 않는다.
- myAI 크기를 그대로 복사하지 않고 현재 방식 대비 실험한다. 초기 탐색 범위 예: 자식 250~500자, 부모 800~1,600자. 실제 토큰 예산·원문 구조·작은 모델의 성능으로 결정한다.
- 2글자 핵심어는 범위가 제한된 정확 검색으로 먼저 보완하고, CJK bigram/한국어 정규화 색인을 기존 trigram과 비교한다. 문서번호·조문번호·부서명은 정확 일치 경로를 유지한다.
- 부모 복원 뒤 중복 제거와 다양성을 적용한다. 다른 값/기간/효력을 가진 판본은 단순 중복으로 제거하지 않는다. 사실 검증은 복원된 원문 범위와 연결한다.

대상: `app/core/chunking.py`, `app/ingest/parsers/`, DB schema/migrations, `notebook_ingest.py`, `app/jobs/pipeline.py`, `fts.py`, `evidence.py`, `rag.py`.

완료 기준: 표 머리글·단위·질문 대상의 관계 보존, 페이지/셀 인용 추적 가능, 기존 대비 근거 Recall 향상, 긴 문서·2글자 용어 평가 개선, 파일명/검색 메타가 원문으로 오인되지 않음.

### 단계 3 — 적응형 검색·후속 질문·선택형 재정렬 (3~5일, P1)

- 모든 일반 질문에 확장을 선행하는 대신 정확한 식별자/명시 항목은 바로 검색한다. 원질문에서 충분한 근거를 얻지 못한 경우에 확장한다.
- 확장 전후의 대상·연도·수량·부정 조건을 비교하고 바뀐 변형은 폐기한다. 유사 변형 수가 많다는 이유로 원질문을 압도하지 않도록 질의 그룹별 총 가중치를 제한한다.
- 후속 질문은 검증된 검색 상태(대상·역할·기간·선택 원문 ID)를 유지하되 AI 답변을 사실 근거로 넣지 않는다. 원질문·실제 독립 질문·선택 범위를 저장하고 사용자가 확인할 수 있게 한다. 자료가 바뀌면 이전 상태를 무효화한다.
- 단계 0에서 규칙 재정렬의 한계가 확인되면 20~40개 후보 대상 로컬 cross-encoder를 별도 어댑터로 실험한다. ONNX/별도 로컬 프로세스 등은 Windows·Python 3.14·PyInstaller·메모리 조건 확인 후 선택한다. Ollama 모델 설치만으로 `/api/rerank`가 생긴다고 가정하지 않는다.
- 모델이 없거나 시간 초과면 기존 규칙 경로로 복귀한다. 후보 재정렬이 근거 사실 검증을 대체하지 않는다.

완료 기준: 확장 on/off와 규칙/모델 재정렬의 독립 비교에서 Recall·정답률 개선, 근거 없는 확정 증가 없음. cross-encoder는 예시 채택 기준으로 nDCG@10 +0.05 또는 정답률 +5%p, 추가 p95 2초 이내를 두고 기준선/장비에 맞게 확정한다. 개선이 없으면 도입하지 않는다.

### 단계 4 — 비교·전체 정리·계산의 완성도 (3~5일, P1)

- 일반 질문, 문서/기간 비교, 집계, 전체 정리를 구분한다. ‘전체 자료의 예산을 비교’ 같은 주제 있는 전체 요청도 고정 Top-K 요약과 구별한다.
- 전체 정리는 문서·절·표 단위 계층적 Map-Reduce로 확장하고 실제 처리한 문서/조각/실패 묶음을 기록한다. 48조각 표집이나 사실 수 제한이 적용되면 완료 범위를 정확히 표시한다.
- 긴 작업에는 진행률·취소·재개와 판본별 map 결과 캐시를 둔다. 문서 해시/질문 목적/프롬프트/모델 프로필이 달라지면 캐시를 무효화한다.
- 합계·차이·증감률은 원문 표의 행/기간/단위를 확정한 뒤 코드로 계산한다. 계산된 값은 입력 셀과 산식을 함께 보여주고, 원문에 없는 숫자라는 이유로 기존 검증이 폐기하지 않도록 ‘직접 인용’과 ‘검증된 계산’을 구분한다.
- ‘현재 유효한 판본’은 승인·시행·대체 관계가 자료에 명시된 경우에만 판단한다. 그렇지 않으면 상충 값과 각 출처를 나란히 보여준다.

완료 기준: 비교 양쪽 자료가 모두 근거에 포함, 집계의 원문 입력과 산식 재현 가능, 전체 정리에서 검토하지 않은 구간을 숨기지 않음, 원문 변경 시 이전 결과 재사용 차단.

### 단계 5 — 규모 대응과 관계 검색 (조건부, 별도 산정)

- 1천/1만/10만 조각에서 검색 p50/p95, 메모리, 색인 시간, 파일 해시 확인 시간을 측정한다. 1,024차원 float32 벡터 자체는 10만 개에서 약 391MiB이며, 현재 적재·정규화 과정의 추가 복사 메모리는 별도다.
- 검색이 실제 병목이면 프로필별 행렬 캐시를 먼저 비교한다. 검색 결과/캐시는 프로젝트·선택 문서·판본·모델·chunker 버전별로 격리한다. 모델 digest/차원/정규화 규칙을 색인 프로필로 고정한다.
- 그래도 예산을 넘거나 공유 서버 요구가 생기면 벡터 저장소 어댑터를 통해 로컬 ANN/Qdrant 등을 검토한다. 개인 Windows 앱 기본 설치에 외부 서비스를 곧바로 필수화하지 않는다. [Qdrant의 하이브리드 검색 API](https://qdrant.tech/documentation/search/hybrid-queries/)는 후보 결합을 제공하지만 업무별 답변 정확도를 대신 보장하지 않는다.
- 관계 검색은 기존 업무–문서–일정–결재/붙임 관계부터 시작한다. 근거 있는 1-hop 조각 보강을 별도 실험군으로 두고, 보강된 모든 조각에 동일 범위·판본 검사를 적용한다. 관계는 원문 근거를 찾는 수단이며 자체 사실 근거가 아니다.

완료 기준: 동일 품질을 유지하면서 측정된 지연/메모리 목표 달성, 서비스 장애 시 제한된 대체 검색과 상태 표시, 관계 확장 on/off 비교에서 다문서 질문 개선.

## 7. 재색인과 출시 전환

청킹을 바꾸면 기존 조각 ID/위치와 대화의 근거가 연결되어 있으므로 단순 `chunks` 삭제 후 재생성을 배포 전략으로 삼지 않는다.

1. 스키마 변경 전 DB 백업을 만들고 새 `index_revision`에 청킹·임베딩을 준비한다. 원문·사용자 교정·노트북 대화·메모는 유지한다.
2. 기존 답변의 `version_hash`, `chunk_id`, locator, 저장된 `exact_quote`를 보존한다. 새 조각으로 연결할 수 없으면 원문 판본/저장 발췌로 보거나 오래된 근거로 표시하며 새 조각에 임의 재연결하지 않는다.
3. 새 색인의 문서 수·조각 수·누락·차원·프로필을 검사하고, 같은 선택 범위로 기존/후보 결과를 비교한다. 작업 중단·재시작을 지원한다.
4. 노트북별 기능 플래그로 전환한다. 결함 시 이전 색인/검색 경로로 돌아갈 수 있게 하고, 이전 색인 삭제는 보존 정책에 따라 별도 수행한다.
5. 파일 추가·삭제·판본 승인·선택 해제·모델 변경·정리 작업 중 원문 변경을 통합 시험한다. 소스 실행뿐 아니라 Windows 번들에서도 확인한다.

## 8. 측정 지표와 채택 기준

아래는 **고도화 목표 초안**이며 현재 달성 수치가 아니다. 단계 0의 기준선과 대상 PC에 맞춰 확정한다.

| 구분 | 측정과 목표 |
|---|---|
| 검색 | 문서/조각별 Recall@20, MRR, nDCG@10을 분리. 문서 Recall은 문서 ID 중복 제거. 후보 Recall@20 95% 이상을 초기 목표로 설정 |
| 문맥 | 최종 문맥에 필요한 원문 근거가 포함된 비율, 표 머리글/단위 보존, 비교 양쪽 커버리지. 검색 성공과 문맥 절단 실패를 분리 |
| 답변 | 답할 수 있는 문항 정답률 90% 이상. 문장별 주장–근거 지지 여부와 인용 정확도 98% 이상 목표 |
| 보류 | 필요한 보류의 정밀도/재현율, 답할 수 있는데 보류한 비율을 동시 보고. 전체 근거 없는 확정 1% 미만 목표 |
| 범위·판본 | 선택 밖/허용되지 않은/오래된 판본으로 확정한 답변 0건. 보조 판정도 범위 일관성 유지 |
| 시간 | warm 일반 질문 p50 10초/p95 20초를 잠정 목표로 설정. 검색 단계 p95 1초, 선택형 rerank 추가 p95 2초. cold 시작과 전체 정리는 별도 집계 |
| 비용·운영 | 질문당 모델 호출 수, 최대 RAM, 색인 시간, 취소 반응 시간, 재개 성공, 대체 경로 비율 |

‘문서에 숫자가 존재한다’와 ‘그 숫자가 질문 대상의 값이다’를 따로 채점한다. 같은 20문항 3회 성공을 60개의 독립 표본 성공으로 표현하지 않는다. 작은 합성 세트에서 오답 0건이 나와도 실제 오류율 1% 미만을 통계적으로 입증한 것은 아니다. 최종 채택에는 충분한 서로 다른 문항과 사람의 근거 검토가 필요하다.

우선 실행 묶음은 **단계 0+1(약 5~8 작업일)**이다. 이 결과를 바탕으로 단계 2~4의 검색/문맥/답변 개선을 진행한다. 재정렬 모델·Qdrant·그래프는 효과가 확인된 항목만 채택한다.

## 10. 후속 구현 기록

단계 0의 평가 CLI·검색 추적과 단계 1의 범위·명시적 인원 역할 검증, 두 글자 용어 검색의 1차 구현·반복 평가 결과는 [노트북 RAG 1차 구현·검증 기록](NOTEBOOK_RAG_STAGE01_2026-10-09.md)에 있다. 전체 계획 완료를 뜻하지 않으며, 개발 세트 전체 비교·최종 확장 on 평가·기관 실자료·구조 보존 청킹 등의 남은 범위를 해당 기록에 명시했다.

2026-10-10의 단계 2는 [부모·자식 검색과 구조 보존 기록](NOTEBOOK_RAG_STAGE02_2026-10-10.md)에 있다. 기존 부모 ID를 유지하며 자식 FTS·벡터로 검색하고 부모 원문으로 인용한다. 같은 날 이어서 긴 섹션의 경계 분할, DOCX 표 머리글과 구조 정보·제목 문맥, 옛 조각을 보관하는 색인 전환(준비·검증·전환·되돌리기), 창 크기 비교를 넣었다. HWPX·PDF의 제목 계층, 실제 기관 문서 평가, 형태소·bigram 색인 비교는 하지 않았다.

같은 기록의 2.5절에 단계 4의 일부(주제 없는 요약 요청의 자동 전체 정리, 묶음 진행 표시, 보류 사유 문구)와 모델 문맥 창 수정이 있다. 단계 4의 계층적 Map-Reduce·map 결과 캐시·코드 계산은 그대로 남아 있다.
