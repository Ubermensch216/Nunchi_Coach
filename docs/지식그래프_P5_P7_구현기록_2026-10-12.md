# 지식그래프 P4 보완·P5 판정 UI·P6 평가·P7 인계 v2 구현 기록

2026-10-12. [P4 검색 구현](지식그래프_P4_검색구현_및_작업인계_2026-10-11.md) 다음으로 남아 있던 연도 기준 UI, 설명·판정 UI(P5), 평가·규모 측정(P6), 인계 형식 2(P7)를 구현했다. 계획의 단계 정의는 [상세구현계획 §9·§11·§12](지식그래프_온톨로지_상세구현계획_2026-10-11.md)를 따른다.

**먼저 결론.** P4의 검색 품질 게이트는 **충족하지 못했다.** 동결 합성 120문항에서 그래프를 켠 비교(B)가 기존 검색(A)과 같고, 모든 질문이 `no_scoped_seeds`로 기존 검색에 물러난다. 따라서 그래프 검색은 계속 기본 off이며 설정 화면에 켜는 항목을 추가하지 않았다. 이번에 사용자에게 열린 것은 검색이 아니라 **설명과 사람 판정(내부 실험 플래그)과 그 인계**다.

## 구현한 것

### 연도 기준 UI (P4 후속)

- 질문 화면의 범위 줄에 ‘연도 기준’(문서 날짜 / 실적 / 평가 / 제출)을 추가했다. 값은 검색 범위의 `year_basis`와 같다. 연도를 고르기 전에는 비활성이고, 기준을 바꾸면 그 기준으로 읽은 연도 목록으로 다시 채워 없는 연도 선택은 풀린다. 기준에 연도가 적힌 문서만 걸러 내며 없는 연도를 보충하지 않는다. 노트북 대화는 선택한 자료가 범위이므로 연도 UI를 두지 않았다.

### P5 — 설명·판정 (`core/knowledge/review.py`)

- 업무의 현재 게시 세대에서 필요한 서식·제출처·담당·기한·금액·근거 문서·대체 관계를 원문 인용(파일·위치·인용문·현재 원문과 일치 여부)과 함께 보여 준다. 거절한 연결도 되돌릴 수 있게 함께 보인다. 대체·충돌 관계는 ‘대체 여부 확정 안 함’으로 양쪽 값과 근거를 함께 보인다.
- 같은 유형·같은 이름인데 서로 다른 개체를 후보로 나란히 보인다(소속 업무·근거 수). 자동으로 합치지 않는다. 사람이 ‘같은 것’(merge)·‘다른 것’(separate)을 고르고 되돌릴 수 있으며, 판정한 쌍은 다시 후보로 올리지 않는다. 방향과 무관하게 같은 쌍으로 본다. 유형이 다르면 거절한다.
- ‘맞음’·‘아님’·되돌리기는 `kg_decisions`에 덧붙이기만 한다. 거절하면 곧바로 근거에서 빠지고 되돌리면 직전 판정으로 돌아간다. 원본 업무·문서·수행 표와 action 실행 승인 경로는 바뀌지 않는다(시험으로 확인). 화면은 ‘맞음은 이 앱의 확인이며 실행 승인이 아님’을 밝힌다.
- 위치: 업무 매뉴얼 탭의 ‘연결 근거’ 카드. 설정 → 화면의 ‘연결 근거 확인(실험 기능)’ 체크 상자(`knowledge_review_ui`)로 켜며 기본은 꺼짐이다. 켜도 검색 결과·답변은 달라지지 않는다.

### P7 — 인계 형식 2 (`core/knowledge/portable.py`, `core/handover_release.py`, `core/transfer.py`)

- 읽기(reader)를 먼저 만들었다. 묶음 형식 1·2와 본체 형식 1·2를 모두 받고, 형식 1에 판정 블록이 있으면 거절한다. 블록은 모양·식별자 중복·종류를 검사한다.
- 쓰기(writer)는 **실을 판정이 있을 때만** 형식 2를 쓴다. 판정이 없는 프로젝트의 인계본·지문은 이전 앱의 것과 같고 이전 앱도 읽는다. 한 번 저장한 스냅샷은 다시 쓰지 않는다.
- 판정의 대상은 번호가 아니라 **설명자**로 적는다 — 개체: 유형·이름·소속 업무명(또는 문서 해시)·연도, 주장: 관계·끝점 설명자·값·정규화한 범위(`task:7:item:deadline` → `task:item:deadline`)·유효 기간·조건. 수신 프로젝트의 UUID·정수 ID·claim_key는 실리지 않는다(시험으로 확인). 인용문 외 본문·절대 경로는 기존 묶음 규칙을 그대로 따른다.
- 받는 쪽은 같은 설명자의 대상이 **정확히 하나**일 때만 적용한다. 없거나 여럿이면 `pending`으로 보존하고(`kg_imported_decisions`, 추가 표), 그래프 투영이 끝난 뒤 다시 시도한다. 받는 쪽에 더 나중의 사용자 판정이 있으면 지키고 `kept_local`로 기록한다. 같은 판정을 두 번 가져와도 한 번만 적용한다. 되돌림은 가져온 판정이 실제로 적용된 경우에만 따라간다. 판정은 `가져옴:<원래 행위자>`로 남는다.
- 가져오기 화면의 결과 안내에 받은 판정 수·적용·대상 미발견·지킨 건수를 보인다. 보고서(report.md)에 판정 요약 절이 들어간다.

### P6 — 평가·규모 (`app/tools/knowledge_scale.py`)

- 기존 `knowledge_eval`의 off/shadow/on 비교를 다시 실행했다. 규모 측정 도구를 새로 만들었다(모델·파서·임베딩 제외, 합성 문서를 직접 DB에 넣어 규칙 추출기와 투영을 돌리고 업무 범위/프로젝트 전체 범위의 그래프 추가 지연·피크 RSS를 잰다).

## P6 측정 결과 (2026-10-12, Windows 11 · 12 논리 CPU · Python 3.14.7 · SQLite 3.50.4)

### 동결 합성 120문항 (모델 OFF FTS, `python -m app.tools.knowledge_eval --graph off|shadow|on`)

| 범주 | 문항(채점) | A 기존 FTS 전부 찾음 / Recall@10 | shadow | B 구조 그래프(on) |
|---|---|---|---|---|
| 단순 | 30 | 30 / 1.00 | 같음 | 같음 |
| 별칭 | 20 | 8 / 0.60 | 같음 | 같음 |
| 연결 | 25 | 5 / 0.50 | 같음 | 같음 |
| 시점 | 25 | 25 / 1.00 | 같음 | 같음 |

범위 밖 노출 0건(세 모드 모두). 게시된 구조 주장 51개, **120문항 전부 `no_scoped_seeds`로 기존 검색에 물러났고 검색 결과 변화 0건**이다. 그래프 조회 p95는 shadow 0.69ms·on 0.48ms로 측정됐지만 시드가 없어 일을 거의 하지 않은 값이다. 로그: `.test_runs/p6/eval-{off,shadow,on}.json`(Git 미포함).

### 규모 (`python -m app.tools.knowledge_scale`, 합성 문서, 모델·파서·임베딩 제외, 웜 캐시, 질문 200~300개)

| 문서 수 | 주장 | DB | 투영 p50 / p95 | 그래프 추가 지연 p95 (업무 범위) | 그래프 추가 지연 p95 (프로젝트 전체) | 피크 RSS(시작→질의 후) |
|---|---|---|---|---|---|---|
| 100 | 180 | 2.1MB | 5.0 / 19.6ms | 1.2ms | 2.6ms | 35→44MB |
| 1,000 | 1,800 | 13.4MB | 11.6 / 38.7ms | 1.5ms | 17.3ms | 35→45MB |
| 10,000 | 18,000 | 126.9MB | 50.6 / 112.0ms | 1.8ms | **150ms 예산 초과 — 300건 모두 기존 검색으로 물러남** | 35→47MB |

- 프로젝트 전체 범위의 별칭 시드 조회가 문서 수에 비례해 느려진다(10,000문서에서 예산 초과). 그래프 검색이 꺼져 있으므로 사용자 영향은 없지만, 검색을 켜기 전에 별칭 후보 조회 방식을 바꿔야 한다.
- 합성 문서는 한 업무의 한 해 공문뿐이고 실제 기관 문서의 관계 밀도·문서 길이와 다르다. 이 수치는 실제 자료의 성능 보증이 아니다.

### 측정 중 발견한 기존 결함과 수정

10,000문서 시험에서 업무 항목 저장(`sync_task_items`)이 **업무가 늘수록 선형으로 느려졌다**(업무 100개째 4.9ms, 600개째 77ms; 10,000문서 합계 499초). 원인은 P3 무효화 트리거(`db/knowledge_dirty.py`)가 행마다 **프로젝트 전체의 현행 주장**을 훑어 근거가 없는 것을 stale로 바꾸던 것이다. 바뀐 파티션의 세대에 근거를 둔 주장만 대상으로 좁히고 `kg_generations(partition_key)` 색인을 추가했다. 수정 후 같은 시험에서 항목 저장은 업무 수와 무관하게 약 2.5ms이고 10,000문서 합계는 5.2초다. 의미는 같다 — 바뀐 파티션이 아닌 주장의 근거는 이 트리거가 바꾸지 않는다(시험 추가). 트리거는 DB를 열 때마다 다시 만들어지므로 기존 프로젝트에도 자동 적용된다.

투영(`project_task`) 자체도 사이클 검사가 모든 활성 세대의 비순환 관계를 읽어 문서 수에 따라 증가한다(표의 투영 p50/p95). 10,000문서에서도 업무당 약 0.1초이며 백그라운드 작업이라 그대로 두었다.

### 게이트(상세구현계획 §12.3) 대조

| 게이트 | 결과 |
|---|---|
| 범위 밖 노출 0건 | 충족(120문항 · 세 모드) |
| 연결 질문 Recall@10, B가 A보다 5%p 이상 | **미충족** — A·B 모두 0.50, 개선 0%p |
| 단순 조회 하락 2%p 이내 | 충족(1.00 → 1.00) |
| 그래프 off일 때 기준선과 동일 | 충족(off 결과 = 이전 기록의 기준선) |
| 1,000문서 그래프 추가 조회 p95 150ms 이내 | 충족(업무 범위 1.5ms · 프로젝트 전체 17.3ms, 웜 캐시·합성) |
| 추가 peak RSS 150MB 이내 | 충족(10,000문서까지 약 +12MB) |
| P8 관계 추출 정밀도 | 해당 없음(모델 관계 후보는 이번 범위가 아니다) |

**결론: 검색 품질 게이트를 충족하지 못했으므로 그래프 검색은 off로 둔다.** 연결·별칭 질문이 개선되지 않는 근본 원인은 구조 추출기가 서술형 문서의 관계를 만들지 못해 질문에서 쓸 시드가 없는 것이다. 서술형 관계 확장(원문 근거 유지)과 별칭·동일성 검색 확장은 P8 이후 과제로 남는다.

## 남은 일

1. **P4 품질 게이트 충족 방법**: 서술형 문서의 관계 추출(규칙 또는 P8 모델 후보)과 별칭 후보 조회 방식 개선 후 같은 동결 질문·규모 시험을 다시 실행한다. 충족 전에는 기본 검색 활성화·설정 항목 추가를 하지 않는다.
2. 벡터 RAG·LLM 답변 A/B, 모델 관계 후보(P8), 실제 기관 자료의 관계 정확도·규모(P9)는 측정하지 않았다.
3. 연결 근거 확인(판정 UI)은 설정의 실험 기능으로만 열려 있다. 실사용자 관찰(전임자/후임자가 판정을 이해하고 인계본으로 이어받는지)과 실제 한글·독립 Windows PC 시험 후 기본 노출을 결정한다.
4. 인계 v2 가져오기는 투영 전에는 판정이 `pending`이며 분석이 끝나야 적용된다. 설명자가 같은 대상이 여럿이거나 보낸 쪽에서 사라진 판정은 적용하지 않고 보존만 한다(화면에서 보존 목록을 보는 UI는 아직 없다). entity·alias·evidence 대상의 판정은 형식은 받지만 적용하지 않고 보존한다.
