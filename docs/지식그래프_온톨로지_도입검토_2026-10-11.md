# 눈치코치 지식그래프·온톨로지 도입 검토

검토일: 2026-10-11 (한국 시간)

재검토 보완: 같은 날 실제 수행 건·산출물·검색 분기·인계 코드를 추가 대조했다. 아래 수행 건 모델과 검색 연결 제안을 수정했으며, 구현 시에는 [상세 구현 계획](<D:/Dev/Nunchi_Coach/docs/지식그래프_온톨로지_상세구현계획_2026-10-11.md>)을 우선한다.

## 1. 판단과 권고

**눈치코치는 업무·문서·근거의 관계를 이미 관리한다. 그러나 공통 개체 식별, 명시적인 관계 의미 체계, 그래프를 이용한 검색을 갖춘 지식그래프는 아직 구현되지 않았다.** 업무 항목과 단계에 관한 암묵적인 도메인 스키마는 있으므로, 관계 관리가 전혀 없는 시스템이라고 설명하는 것도 부정확하다.

도입을 권고한다. 업무 복원에서 중요한 것은 비슷한 문서를 찾는 것에 더해, 업무·담당 기관·필요 서식·산출물·법령·전년도 사례의 연결을 설명하는 것이다. 다만 지식그래프가 자료를 더 정확하게 읽거나 AI 답변을 자동으로 사실로 만드는 것은 아니다. 잘못 추출한 관계가 여러 답변에 반복 사용되는 문제도 생길 수 있다.

**추천 조합: 현재 프로젝트 SQLite + 업무 중심 개체·주장·근거 모델 + RDFLib·pySHACL + 기존 검색에 그래프 검색을 추가하는 방식.** myAI의 제한된 유형과 검색 확장 설계, TONGDAL.ai의 개체 정규화·문서 판본별 근거 설계를 재사용하되 아래에 확인한 약점은 보완한다. 별도 그래프 서버 도입은 초기 필수 조건으로 두지 않는다.

이 문서는 분석과 설계 제안이다. 제품 코드·DB 스키마·실행 의존성을 변경하거나 외부 라이브러리를 설치하지 않았다.

## 3. 눈치코치의 현재 관계 관리

| 현재 구조 | 관리하는 관계 | 지식그래프로 확장할 때 활용 |
|---|---|---|
| `tasks`, `task_docs` | 업무와 문서의 다대다 연결, 자동/사람 배정 | 업무와 근거 문서 연결의 출발점 |
| `task_items` | 업무의 목적·기한·금액·서식·제출처 등 유형별 내용 | 개체·속성·주장으로 구조화할 후보 |
| `work_steps` | 수행 순서, 입력·서식·산출물, `after_step_id` 선행 단계 | 절차와 단계 관계 |
| `evidence` | 항목/단계/공백과 문서 해시·위치·인용문 | 그래프 주장 근거와 판본 검증 |
| `task_cycles`, `task_steps` | 주기와 연도별 과거 처리 사례 | 업무 유형과 연도별 수행 건 구분 |
| `work_cases` | 특정 업무·연도·회차의 실제 수행 건과 기한·근거 상태 | 실제 TaskCase의 정본으로 재사용; 과거 사례를 자동 실행 건으로 만들지 않음 |
| `action_runs`, `action_steps`, `artifacts` | 실행·승인·산출물 판본과 대체 관계 | 실제 실행과 산출물 관계를 상태·출처와 함께 투영 |
| `doc_years` | 작성·실적·평가·제출연도 | 문서 작성연도와 업무 적용연도 구분 |
| `version_groups`, `version_members` | 문서 판본 후보와 최신본 제안 | 판본 연결 후보; 실제 대체 효력과는 구분 |
| `source_records`, `source_assets` | 수집 출처, 본문·붙임 연결 | 원본 출처와 수집 이력 |

현재 검색은 벡터와 FTS5 순위를 결합한 뒤 재정렬·검증한다. 그래프 후보를 추가하는 경로는 없다. 실제 연결은 변형 질의가 순위를 다시 만드는 `_with_variants()` 뒤, `_select_context()` 전에 해야 한다. `QueryScope`는 문서·업무·연도 범위를 관리하며 현재 연도는 `documents.eff_year` 기준이다. 향후 업무연도와 문서연도를 명시적으로 구분하고 모든 검색 경로에 같은 범위를 적용해야 한다.

문서 내용이나 파서가 바뀌면 `invalidate_document_analysis()`가 자동 분석·조각을 무효화하고 사람의 교정은 보존한다. `WorkStore.evidence_for()`는 저장한 문서 해시와 현재 해시를 비교해 근거의 유효성을 표시한다. 그래프에도 같은 계약을 확장하는 것이 적합하다.

확인하지 못한 현재 기능은 공통 개체/별칭 저장소, 유형별 관계의 출발·도착 개체 제약, 관계의 적용 기간, 관계 경로를 이용한 검색, RDF/OWL/SHACL 검증이다. SQL 외래키가 있다는 사실만으로 이 기능들이 구현되었다고 볼 수 없다.

## 4. myAI 분석

### 구현된 부분

- 온톨로지 v1.0에 개체 10종과 관계 7종을 명시한다. 개체는 문서·개념·부서·역할·절차·규정·서식·시스템·법령·조문이다. 관계는 관련·근거·담당·요구·소속·대비·조문 참조이다.
- 추출 프롬프트와 출력 검증에서 허용 유형을 제한한다. 법령·조문 개체와 조문 참조 관계는 LLM의 자유 생성에서 제외하고 규칙 기반 인용 수집 경로로 만든다. 해당 규칙 매칭 자체가 공식 법령의 존재·현행 효력을 보증하는 것은 아니다. 조문 본문은 답변 시 공식 조회 경로로 확인하는 설계다.
- 노트북별 `graph.sqlite`에 `kg_nodes`, `kg_aliases`, `kg_edges`, `kg_source_refs`, `kg_meta`를 저장한다. 노드와 관계에 문서 ID·조각 번호·인용을 연결한다.
- 별칭으로 시작 개체를 찾고 **1단계 이웃**을 탐색하여 추가 문서 조각을 검색한다. 실제 RAG에서 벡터·키워드 순위와 결합하고 재정렬한다. 임의 길이의 다단계 추론이 구현되었다는 뜻은 아니다.
- 임시 DB에 그래프를 재구축하고 무결성을 검사한 뒤 교체하며, 수동 활성/비활성 판정을 가능한 동일 ID에 다시 적용한다.
- 그래프 검색 ON/OFF를 비교하는 A/B 평가 도구가 있다. Recall@K·MRR·Precision·근거 없음 등을 측정한다. 도구의 존재를 성능 향상의 실측 증거로 해석하지 않았다.

주요 근거: [온톨로지](https://github.com/Ubermensch216/myAI/blob/e811af19ad1ef9765fb6ec349e36e6dca6e3c73a/server/rag/graph/ontology.js), [저장소](https://github.com/Ubermensch216/myAI/blob/e811af19ad1ef9765fb6ec349e36e6dca6e3c73a/server/rag/graph/store.js), [검색 결합](https://github.com/Ubermensch216/myAI/blob/e811af19ad1ef9765fb6ec349e36e6dca6e3c73a/server/rag/departmentRag.js), [A/B 평가](https://github.com/Ubermensch216/myAI/blob/e811af19ad1ef9765fb6ec349e36e6dca6e3c73a/scripts/eval-graph-ab.mjs).

### 그대로 이식하면 안 되는 부분

1. **원문 인용 검증이 강제 거부 조건이 아니다.** 추출 검증은 인용이 원문에 실제 존재하는지 확인하지 않는다. 신뢰 점수 함수는 불일치에 감점하지만, 높은 모델 자기점수와 인용 길이 보정 등으로 활성화 기준을 넘을 수 있다. 눈치코치에서는 점수 계산 전에 인용의 존재·판본·위치를 검사해야 한다. 인용이 존재하더라도 그 문장이 관계를 실제 지지하는지는 별도 검증이 필요하다.
2. **이름 중심 개체 ID의 범위가 부족하다.** 유형+정규화 이름으로 ID를 만든다. 다른 기관의 같은 이름 부서나 다른 연도의 같은 이름 행사가 합쳐질 수 있다. 유형·기관·업무 수행 건·식별자를 고려해야 한다.
3. **근거에 문서 판본 해시가 없다.** `document_id + chunk_index`만으로 재파싱 뒤 같은 내용을 가리킨다고 보장할 수 없다. 눈치코치의 기존 문서 해시 계약을 추가해야 한다.
4. **1단계 이웃의 근거와 관계 자체의 근거가 다르다.** 현재 확장기는 이웃 노드의 source refs를 가져온다. 노드가 언급된 조각이 관계의 방향·조건을 설명하지 않을 수 있으므로, 눈치코치에서는 traversed edge의 검증된 근거까지 가져와야 한다.
5. **전체 노트북 조각 로딩은 대량 자료에서 부담이다.** 그래프 보충 후보를 복원할 때 모든 조각을 로딩하는 경로가 있다. ID로 필요한 조각만 가져오도록 바꿔야 한다.

**재사용 판단:** 제한된 어휘, 출력 검증, 작은 범위의 이웃 탐색, 검색 결합, 수동 판정 보존, A/B 평가 설계는 재사용 가치가 높다. JavaScript 모듈을 눈치코치에 그대로 넣기보다는 Python과 기존 DB 계약에 맞게 이식한다. 현재 구조는 실용적인 유형 기반 온톨로지이며, RDF/OWL 추론·SHACL 검증을 갖춘 표준 온톨로지 시스템과는 구분한다.

## 5. TONGDAL.ai 분석

### 구현된 부분

- Python/SQLite에 `entities`, `entity_aliases`, `relations`, `relation_evidence`를 둔다. 행안부→행정안전부, 부산시→부산광역시 등의 사전으로 기관명을 통일한다.
- 관계에 문서 ID·판본 ID·조각 ID·근거 텍스트를 연결한다. `source_documents`, `source_versions`가 안정적인 문서 정체성과 판본을 관리한다.
- 허용 관계 11종에 `SUPERSEDES`, `SUPPORTS`, `CONTRADICTS`, `DERIVED_FROM` 등이 있다.
- LLM으로 문서 조각의 주어·관계·목적어를 추출한다. 긴 문서는 전체에 걸쳐 **최대 15개 조각을 표본 추출**한다.
- 검색·그래프 표시·관계 숨기기 UI/API가 있다. 검색은 검색된 조각의 관계와 질문 단어에 맞는 관계를 부가 정보로 제공한다.

주요 근거: [개체 통일·관계 저장](https://github.com/Ubermensch216/TONGDAL.ai/blob/d5300834f0b7c26dca3b9f65a0a32db9e3bf2c44/electron/sidecar/app/knowledge/entities.py), [DB 구조](https://github.com/Ubermensch216/TONGDAL.ai/blob/d5300834f0b7c26dca3b9f65a0a32db9e3bf2c44/electron/sidecar/app/core/database.py), [추출·검색·그래프 API](https://github.com/Ubermensch216/TONGDAL.ai/blob/d5300834f0b7c26dca3b9f65a0a32db9e3bf2c44/electron/sidecar/main.py).

### 그대로 이식하면 안 되는 부분

1. **새 개체 저장소와 실제 검색 경로가 분리되어 있다.** `entities/relations`에도 쓰지만 검색·그래프 API·숨기기 경로는 여전히 `graph_triples`를 사용한다. 새 저장소의 정규화가 실제 그래프 검색에 전부 반영된 상태가 아니다. 눈치코치는 하나의 정본에서 검색·화면을 파생해야 한다.
2. **추출 어휘와 저장 어휘가 다르다.** 프롬프트의 `WORKS_ON`, `PART_OF` 등은 `VALID_PREDICATES`에 없다. 새 관계 저장 함수는 허용하지 않는 관계를 `RELATED_TO`로 바꾼다. 관계 의미가 사라지므로 공통 스키마로 추출·검증·저장을 일치시키고, 모르는 관계는 후보로 보류해야 한다.
3. **유형·기관 맥락을 고려하지 않고 같은 이름을 합칠 수 있다.** 별칭 또는 canonical name 조회에 개체 유형 조건이 없다. 이름이 같다는 이유만으로 사람·기관·개념이나 서로 다른 기관의 부서를 합쳐서는 안 된다.
4. **관계 근거가 관계를 지지하는 정확한 구절은 아닐 수 있다.** 저장 시 `chunk.text[:300]`을 넘긴다. 해당 관계가 조각의 뒤쪽에 있으면 근거 텍스트에 포함되지 않을 수 있다. 정확한 인용과 원문 오프셋 또는 구조 위치가 필요하다.
5. **표본 추출과 관계 갱신의 한계가 있다.** 최대 15개 조각은 전체 관계 추출을 보장하지 않는다. 확인한 재색인 경로는 기존 `graph_triples`를 삭제하지만 새 `relations/relation_evidence`의 중복·구판 무효화를 함께 처리하지 않는다. 표본 처리 범위와 실패를 기록하고 판본에 따른 유효성을 관리해야 한다.

**재사용 판단:** 개체·별칭·문서 판본·관계 근거의 개념과 Python 구현 방식은 눈치코치와 잘 맞는다. 그러나 저장 함수와 이중 관계 저장 경로를 그대로 복사하기보다 단일 정본·유형 제약·정확한 근거·갱신 계약을 먼저 갖춘다. 허용 관계명에 `SUPERSEDES`가 있다는 것과 대체 관계를 정확하게 판정하는 기능이 있다는 것도 구분한다.

## 6. 핵심 함수의 분리 실행 확인

외부 모델이나 실제 사용자 DB를 열지 않고, 원본 코드를 변경하지 않는 방식으로 확인했다.

| 확인 방법 | 관측 결과 | 해석 |
|---|---|---|
| myAI `scoreRelationConfidence()`에 원문에 없는 긴 인용, 모델 점수 0.95, `BASED_ON` 입력 | 점수 **0.933**, 기본 활성화 기준 **0.6** 초과 | 이 함수의 점수만으로 원문 지지 여부를 보장할 수 없음. 전체 모델의 오류율 측정은 아님 |
| TONGDAL 개체 모듈을 메모리 SQLite에서 호출 | 부산시와 부산광역시의 ID가 같음 | 기관 별칭 정규화는 동작 |
| 같은 이름을 Organization과 Concept 유형으로 각각 등록 | ID가 같음 | 유형이 다른 개체도 합쳐질 수 있음을 재현 |
| 같은 `WORKS_ON` 관계를 두 번 저장, 조각 ID는 None | `RELATED_TO` 두 행, 근거 0행 | 어휘 의미 손실·중복·근거 없는 관계 허용을 재현 |

이 결과는 특정 함수 계약을 확인한 것이다. 두 프로젝트의 전체 품질, 운영 데이터의 상태, 실제 질문 정답률을 판정한 결과는 아니다.

## 7. 눈치코치에 맞는 의미 모델

온톨로지는 업무를 표현하는 **유형·관계·제약의 규칙**, 지식그래프는 그 규칙으로 저장한 **구체적인 업무 사실과 연결**, 그래프 검색은 이 연결을 따라 **원문 근거를 찾는 방법**으로 구분한다.

### 우선 개체와 관계

| 개체 | 의미 | 기존 자료와 연결 |
|---|---|---|
| TaskType | 반복되는 업무 종류 | 기존 `tasks`를 초기 연결 대상으로 사용 |
| TaskCase | 특정 연도·회차의 실제 수행 건 | 기존 `work_cases` 정본 연결; 기관 범위는 별도 근거로 연결. 과거 문서의 추정 사례는 구분 |
| Step | 수행 단계 | `work_steps`, `task_steps` |
| Organization / Role | 기관·부서·역할 | 제출처·담당 항목, 기관별 별칭 |
| Form / Artifact | 사용할 서식·만들 산출물 | 서식·산출물 항목, 실제 파일 및 기존 `artifacts` 판본·대체 관계 |
| DocumentVersion | 문서의 특정 내용 판본 | 문서 식별자·내용 해시; 파서/조각 버전은 별도 분석·색인 이력 |
| Regulation / Article | 규정·조문과 해당 판본 | 원문 인용, 필요한 경우 기존 법령 조회 |
| Claim | 관계 또는 속성이 성립한다는 주장 | 기한·금액·담당·필요자료 등, 근거와 확인 상태 |

우선 관계는 `DOCUMENTS_CASE`, `HAS_STEP`, `PRECEDES`, `OWNED_BY`, `SUBMITTED_TO`, `REQUIRES_FORM`, `PRODUCES`, `BASED_ON`, `SUPERSEDES`로 제한한다. 예를 들어 `REQUIRES_FORM`의 출발은 수행 건 또는 단계, 도착은 서식이어야 한다. 날짜·금액은 모든 값을 개체로 만들기보다 타입·단위가 있는 주장 값으로 저장한다.

다음 예시는 설계 예시이며 실제 문서에서 추출한 사실이 아니다.

```text
업무 종류: 보조금 정산
  └─ 2025년 특정 기관의 수행 건
       ├─ 담당 → 복지지원과
       ├─ 필요 서식 → 정산서 서식 v3
       ├─ 선행 단계 → 증빙 취합
       └─ 제출기한 주장 → 2025-03-31
              ├─ 근거 → 2025년 요청공문 특정 판본·표 1
              ├─ 확인 → 자료에서 추정 / 담당자 확인
              └─ 대체 후보 → 변경공문의 2025-04-07 주장
```

2024년과 2025년 기한을 같은 업무 개체의 단일 속성으로 덮어쓰지 않는다. 최신 작성일이나 파일명의 '최종'만으로 옛 기한을 무효화하지 않는다. 같은 수행 건·속성·적용 조건에 관한 명시적인 변경 근거가 있을 때만 대체 관계를 확정한다.

### 주장·근거 저장

개략 구조는 개체·별칭·주장·근거·투영 이력이다. 재검토 결과 기존 정본 binding, 사용자 판정, 주장 간 충돌·대체, 증분 작업/분석 세대도 필요하다. 상세 테이블 계약은 상세 구현 계획 5절을 따른다. 주장에는 관계 양끝 또는 타입이 있는 값, 수행 건·기간·조건·생성 규칙/모델·온톨로지 버전을 기록한다. 기존 `workstate.py`의 근거·적용성·사람 확인·수행 상태를 유지하고 검증·수명 상태를 분리한다. 근거에는 문서 식별자·내용 해시·분석 fingerprint·정확한 인용·구조 위치를 기록하며 변경 가능한 chunk ID만으로 식별하지 않는다.

적용 시각(`valid_from/to`)과 시스템이 알게 된 시각(`recorded_at/retracted_at`)을 구분한다. 기간을 모르면 추정해서 채우지 않고 unknown으로 남긴다. 서로 충돌하는 주장은 각각 보존하고 대체·충돌 연결을 둔다. 기존 사용자 확인/거절 상태를 유지하며, `stale` 판본의 주장도 이력에는 남기고 현재 답변의 확정 근거에서는 제외한다.

개체 ID는 프로젝트·유형·기관/업무 맥락과 안정 ID를 이용한다. 별칭은 다의성을 허용한다. 같은 '복지과'가 여러 기관에 있을 때 단일 전역 별칭에 강제로 합치지 않는다. 사용자에게 합치기 후보와 근거를 제시하고 분리도 가능하게 한다.

## 8. 데이터 생성과 검색 방식

1. **기존 구조에서 먼저 만든다.** 업무-문서 연결, 단계 선후, 근거, 공식 문서 본문-붙임 등 구조화된 관계부터 투영한다. 자동 배정·추정의 상태는 그대로 유지한다. SQL에 저장돼 있다는 이유로 '확정 사실'로 승격하지 않는다.
2. **규칙으로 추출할 수 있는 것을 우선한다.** 표의 기한·단위·제출처와 명시된 문서번호 등은 기존 추출기를 재사용한다. 일반적인 대명사·다의적인 기관명은 자동 동일 개체 확정에서 제외한다.
3. **LLM은 관계 후보를 보충한다.** 허용 스키마와 정확한 인용을 출력하게 한다. 인용의 원문 존재·위치·판본을 먼저 검사하고, 관계의 방향·조건·의미가 인용으로 뒷받침되는지 별도 검사한다. 모델 자기점수는 확인 완료나 정답 확률로 사용하지 않는다.
4. **처리 범위를 기록한다.** 총 대상 조각, 방문 조각, 규칙 처리, 모델 처리, 실패·생략 이유를 구분한다. 표본 그래프를 전체 문서의 완전한 지식으로 표시하지 않는다. 추출 실패로 문서의 기존 검색 가능성이 사라지지 않게 한다.
5. **검색에 후보 경로를 추가한다.** 기존 벡터/FTS 검색과 병행하여 질문 개체→허용 관계→검증된 근거 조각을 찾는다. 초기에는 1단계, 필요 시 2단계까지만 제한된 관계로 확장하고 방문 수·시간·보충 조각 예산을 둔다. 이는 시작 설계이며 성능 시험으로 조정한다.
6. **기존 범위를 모든 경로에 적용한다.** `QueryScope`의 노트북 선택 자료·업무·연도를 개체 검색, 각 관계 근거, 최종 후보에 적용한다. 선택 범위 밖 근거에만 의존하는 연결도 답변에 들어오지 않게 한다. 재정렬 뒤 잘라내기만 하면 후보 예산이 범위 밖 자료에 소모되므로 탐색 단계부터 제한한다.
7. **원문을 답변의 근거로 사용한다.** 관계 경로의 각 연결에 근거를 붙이고 현재 인용·수량 검증기를 통과시킨다. 그래프 요약을 원문 인용처럼 표시하지 않는다. 여러 단계 연결이 실제 인과·법적 의무를 뜻한다는 추론은 별도 승인된 규칙 없이는 하지 않는다.

모델 OFF 상태에서도 기존 업무 관계를 SQL로 탐색하고 자료를 검색할 수 있게 한다. 그래프 기능 실패 시 기존 검색 경로를 유지한다. 사용자 화면은 '왜 필요한가', '어떤 문서가 근거인가', '무엇이 바뀌었나'를 먼저 보여준다. 복잡한 전체 노드 그림은 후순위다.

의미 체계는 작은 업무 전용 어휘로 시작하고 다음 표준의 필요한 부분을 매핑한다.

- **SKOS:** 업무 분류의 상하위 개념·대표 이름·대체 이름. 기관 개체의 동일성 판정 전체를 SKOS 별칭만으로 대체하지 않는다. [W3C SKOS](https://www.w3.org/TR/skos-reference/)
- **PROV-O:** 원본·추출 활동·생성 주체·파생 자료의 출처 연결. 문서 판본 해시와 실행 ID를 연결한다. [W3C PROV-O](https://www.w3.org/TR/prov-o/)
- **RDFS/필요한 OWL 표현과 SHACL:** 유형과 관계를 명시하고 구조 제약을 검사한다. 광범위한 OWL 추론은 초기 필수 범위에 넣지 않는다. OWL의 개방 세계 가정만으로 '없어야 할 필드'나 '필수 근거 누락'을 검사할 수 있다고 가정하지 않는다. [W3C SHACL](https://www.w3.org/TR/shacl/)

RDFLib·pySHACL은 초기에 개발/검증 도구로 도입할 수도 있다. 사용자 실행물의 상시 의존성으로 포함할지는 동적 사용자 온톨로지 검증이 필요한지와 패키징 결과에 따라 결정한다. 고정 스키마의 핵심 런타임 검사는 SQL/Python에서 먼저 강제한다. 외부 라이브러리 도입 시 고정 버전·의존성 잠금·기존 고지문에 해당 라이선스를 포함한다.

## 10. 적용 순서와 코드 접점

| 순서 | 작업 | 완료 판단 |
|---|---|---|
| 1. 의미 계약 | 업무 유형/수행 건, 개체 유형, 관계 방향·양끝 유형, 주장 상태·근거 계약 확정 | 기한 변경·동명이 부서·연도별 사례 등 대표 질문을 스키마로 표현 가능 |
| 2. 기존 데이터 투영 | 현재 SQLite에 그래프 테이블과 마이그레이션, 기존 관계를 상태와 함께 투영 | 모델 없이 탐색 가능; 기존 UI·검색·사용자 교정 보존 |
| 3. 근거·판본 갱신 | 문서 변경/재파싱/삭제 시 영향 주장만 무효화, 새 근거 생성과 원자적 반영 | 오래된 인용이 현재 근거로 재사용되지 않음; 중단·재개와 인계본 복원 검증 |
| 4. 검색 확장 | 제한된 개체·관계 탐색을 RAG 후보에 결합 | 기존 검색과 같은 자료 범위 준수; A/B 개선과 악화 모두 보고 |
| 5. 모델 후보 추출 | 원문 검증·처리 범위 기록·사용자 확인을 갖춘 추출 | 잘못된 관계가 확정 사실로 승격되지 않음; 자원·시간 예산 충족 |
| 6. 사용자 기능 | 필요한 서식/담당/변경 이력에 '연결 이유와 근거' 제공 | 실제 인수인계 과제의 확인 시간·성공률 개선 |
| 7. 저장 엔진 재평가 | 필요한 경우 LadybugDB 또는 Oxigraph 비교 | SQL 관계 탐색의 병목이 실측되고 새 엔진의 전체 비용이 더 낮음 |

코드 접점 제안:

- `app/db/migrations.py`: 다음 스키마 버전의 그래프 테이블·인덱스. 기존 업무·문서 ID 연결과 외래키·중복 제약을 명시한다.
- `app/db/repo.py:130`: `invalidate_document_analysis()`와 문서 내용 변경에서 그래프 판본·주장 무효화를 함께 처리한다.
- `app/db/workstore.py`: 항목·단계·근거와 사람 교정의 정본을 계속 유지한다. 그래프에 같은 정보를 별도 수정 가능한 정본으로 중복 저장하지 않는다.
- `app/core/knowledge/` (새 모듈 제안): ontology, projection, entity_resolution, claims, validation, lifecycle을 분리한다.
- `app/search/graph.py` (새 모듈 제안): 범위가 적용된 제한 탐색으로 원문 조각 ID와 관계 근거를 반환한다.
- `app/search/rag.py`: `_with_variants()` 이후 `_select_context()` 이전에 그래프 후보를 추가한다. 그래프 후보가 기존 의미 유사도 한도에 의해 모두 제거되지 않도록 후보 자격도 설계하되, 원문 지지 검사와 기존 답변 검증은 유지한다. `search_only`·직접 필드 답변·노트북 overview는 별도 분기 계약과 시험이 필요하다.
- `app/search/query.py`: 그래프의 모든 단계에서 동일한 QueryScope를 적용한다.
- 분석 작업·진단·백업/인계: 그래프 추출 범위와 버전, 중단·재개, 사용자 개체 병합/관계 거절을 보관한다. 단순 재생 색인과 반드시 보존할 사람 판정을 구분한다.

그래프 투영은 문서 해시·파서 버전·온톨로지/추출기 버전·사용자 교정 revision에 종속시킨다. 자동 변경은 같은 DB 트랜잭션 또는 명시적인 dirty revision/작업 큐를 이용해 반영한다. 별도 엔진을 붙이더라도 SQLite 정본에서 재생할 수 있게 한다.

## 11. 검증 계획

대표 평가 질문은 단순 검색, 별칭, 서로 다른 기관의 동명이 부서, 여러 문서 연결, 연도별 담당/기한, 변경 공문의 대체, 실제 충돌, 표 뒤쪽의 관계, 선택 자료 밖 연결, 원본 변경, 모델 OFF를 포함한다. 평가셋은 수정 전에 동결하고, 가능한 실제 기관 비식별 자료와 독립적인 정답 검토를 사용한다.

| 항목 | 비교·검사 |
|---|---|
| 개체·관계 정확성 | 개체 오병합/오분리, 관계 유형·방향·조건의 정밀도·재현율; 정확한 근거 매칭 |
| 검색 | 기존 검색 vs 기존+구조화 그래프 vs 기존+모델 보충 그래프; Recall@K·MRR·Precision |
| 답변 | 근거 없는 확정, 연도/기관 혼동, 충돌·보류 적절성, 관계 경로별 인용 정확성 |
| 범위 | 선택한 자료/업무/연도 밖 근거 노출, 경로 중간의 범위 위반 |
| 수명주기 | 재파싱·원본 변경·삭제·재색인·강제 종료 후 구판 근거 재사용, 사용자 거절/수정 보존 |
| 규모 | 100·1,000·10,000개 문서의 단계별 시간, 관계 수, RSS 메모리, DB 크기, 검색 p50/p95; 10,000개는 향후 시험 목표이고 검증 완료 규모가 아님 |

범위 위반·원문에 없는 인용·구판을 현행 확정 사실로 사용한 사례는 동결된 회귀 세트에서 0건이어야 한다. 이는 그 세트의 합격 조건이며 모든 미래 입력의 무오류 보장은 아니다. 관계 추출의 목표 정밀도·허용 추가 처리 시간은 기준선 측정과 사용자 업무 중요도에 따라 확정한다. 기존 단순 질문이 나빠지는 비율도 함께 보고한다.

모델 비용은 파일 수보다 **처리 조각 수 × 조각당 모델 호출 수 × 호출 시간**에 크게 좌우된다. 본문 읽기, 그래프 후보 추출, 개체 통일, 관계 검증을 따로 계측한다. 우선 기존의 구조화 관계를 투영하고 선택한 중요 업무에 모델 추출을 추가하는 방식으로 초기 부담을 줄인다. 그래프 자체가 현재 200MB/200만 자/시트당 2만 셀의 파서 한도를 늘려주지는 않는다.

## 12. 도입 의사결정

**즉시 착수할 가치가 있는 범위는 '업무 수행 건·개체·주장·근거의 의미 계약'과 '기존 데이터로 만드는 경량 그래프'다.** 그다음 기존 검색과 A/B 비교하여 모델 관계 추출과 검색 확장의 실제 효용을 판단한다.

외부 의존성은 RDFLib·pySHACL을 첫 검증 후보로, Graphiti는 시간 모델 참고로, LightRAG는 비교 실험 대상으로 둔다. LadybugDB/Oxigraph는 규모에 따른 병목이 확인된 후 고려한다. Microsoft GraphRAG는 전체 자료 요약이 중요해지는 경우에 별도 비교한다.

myAI와 TONGDAL.ai의 가장 가치 있는 공통 원리는 **유형을 정한 관계와 원문 근거를 연결하는 것**이다. 눈치코치에서는 여기에 수행 연도·기관 범위·문서 판본·사용자 확인·추출 범위를 추가해야 실제 인수인계에 쓸 수 있는 지식그래프가 된다.
