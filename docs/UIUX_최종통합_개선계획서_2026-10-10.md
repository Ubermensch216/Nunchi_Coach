## 1. 최종 결정

**대메뉴는 `오늘 · 업무 · 자료 · 노트북` 네 개로 재편한다.**

- **오늘:** 업무를 고르기 전에 확인할 제안, 기한, 승인 대기, 실패, 진행 중인 일과 재개 경로.
- **업무:** 맡은 업무를 이해하고, 대상 연도의 수행을 진행하는 중심. `목록 | 일정`을 상시 제공한다.
- **자료:** 원문 탐색·판본·근거 확인과 별도 보기인 `만든 문서`.
- **노트북:** 선택한 자료로 질문·비교·정리·초안을 만드는 독립 작업 공간. 업무에서 맥락을 전달하여 바로 들어올 수도 있다.

자료가 연결된 일반 프로젝트의 기본 진입은 **항상 오늘**이다. 새 프로젝트는 시작 안내, 노트북만 사용하는 프로젝트는 노트북 시작·재개 경로를 제공한다. 제안의 유무에 따라 기본 진입 메뉴를 바꾸지 않는다. 명시적인 노트북·업무 링크를 여는 경우에는 그 목적지를 우선한다.

‘노트북’ 명칭은 이번 개편에서 유지하고 `자료에 질문하고, 비교·정리해 문서로 남기기`를 화면에 설명한다. ‘AI 작업실’은 후속 명칭 시험 후보로 남긴다. ‘문서’ 대메뉴는 ‘자료’로 바꾸되, 실제 파일을 가리키는 문맥의 ‘문서’까지 일괄 치환하지 않는다.

기술적으로는 **프로젝트 실행 서비스, 공통 챙길 일 조회, 명시적 업무 맥락 연결, 산출물 통합 조회**를 먼저 정리한다. 기존 실행기·승인 규칙·자료 범위 검사·근거 판본을 재사용한다.

이 문서는 이번 개편의 통합 기준으로 제안한다. A·B는 비교·결정 이력으로 보존하며, 구현 시 README와 최상위 제품 기준 문서에 본 계획의 확정 구조를 반영한다. 여기서 계획을 작성한 것이 제품 구현 완료를 뜻하지는 않는다.

## 4. 화면과 이동 구조

```text
프로젝트
 ├─ 오늘
 │   ├─ 조치 필요: 승인 대기 · 실패/중단 · 확인된 기한
 │   ├─ 새 제안 / 열린 제안
 │   ├─ 진행 중 · 이어서 할 일
 │   └─ 인수인계 시작 안내 · 전체 업무 · 업무 일정 · 노트북
 ├─ 업무
 │   ├─ [목록 | 일정]   ← 업무 영역 공통 머리에서 접근
 │   └─ 업무 상세 + 대상 연도 / 수행 건 선택
 │       ├─ 지금 할 일
 │       ├─ 준비 작업
 │       ├─ 자료: 먼저 읽을 자료 + 전체 자료
 │       ├─ 언제 하는 일인가
 │       └─ 어떻게 처리했나
 ├─ 자료
 │   ├─ 원문·자료원·판본·분석 상태
 │   └─ 만든 문서
 └─ 노트북
     ├─ 작업 묶음 목록
     └─ 출처 | 대화 | 스튜디오
         └─ 업무·연도·수행 건 맥락 + 선택 자료 범위 표시
```

### 4.1 오늘

‘오늘’은 오늘 마감인 일만 표시하는 화면이 아니다. 부제는 ‘지금 챙길 일과 이어서 할 일’로 두고 각 항목에 실제 기한과 해당 연도를 표시한다.

- 조치 필요 항목은 기한 초과·임박, 승인 대기, 실패·중단 등 이유를 표시한다. 과거 패턴은 확정 마감과 같은 긴급도 표시를 쓰지 않는다.
- 진행 중인 일을 선택하면 **그 수행 건의 해당 실행**으로 이동한다. 최신 실행을 임의로 대신 열지 않는다.
- ‘새 제안’과 ‘검토 중인 제안’을 구분한다. 읽었다는 이유만으로 카드가 사라지거나 처리 완료가 되지 않는다.
- 누적 완료 수는 오늘의 핵심 지표에서 빼고 실행 이력에 둔다. 기간 한정 완료 수를 보여 줄 경우 기간을 함께 표시한다.
- 값이 0이면 숨김·빈 상태를 일관되게 사용한다. 무엇을 분석했고 무엇은 아직 살피지 못했는지 설명한다.

빈 상태는 구분한다.

| 상태 | 보여 줄 내용 |
|---|---|
| 새 프로젝트·자료 없음 | 폴더 연결, 노트북 시작 또는 기존 노트북 재개 |
| 자료 준비 중 | 준비 범위·진행·먼저 볼 수 있는 업무/자료 |
| 조치할 일 없음 | ‘현재 확인된 챙길 일이 없습니다’와 최근 수행·전체 업무·일정 접근 |
| 인수인계 확인 미완료 | `handover.next_step()`을 활용한 다음 확인 항목. 업무 수행 마감과 분리 |
| 분석 실패·일부 자료 누락 | 확인하지 못한 범위와 재시도·자료 확인 경로 |

빈 화면을 채우기 위해 거절·미루기한 제안을 다시 추천하지 않는다. 지난달·이번 달의 과거 자료는 보조 정보로 표시할 수 있으나 새 제안이나 올해의 의무로 계산하지 않는다.

### 4.2 업무와 일정

업무 영역의 얇은 컨테이너가 목록·일정·상세 이동을 담당한다. 기존 `TasksView`와 `CalendarView`를 재사용하고 공통 머리에서 목록·일정에 접근할 수 있게 한다. 현재 상세를 떠났다가 돌아오면 업무·연도·탭·검색·스크롤을 복원한다.

일정은 전 업무를 대상으로 하며 **확정 기한 / 준비 권고 / 과거 패턴**을 구분한다. 기존 ‘지금 챙길 일’ 탭은 독립적인 행동 목록으로 유지하지 않는다. 과거 문서 탐색으로 역할을 좁히거나 공통 챙길 일 조회의 일정 필터를 사용한다. 확정 기한의 출처는 공식 문서 또는 담당자 확인이어야 한다.

업무 상세의 ‘지금 할 일’은 업무 개요·근거·확인할 정보·다음 단계, ‘준비 작업’은 선택 수행 건의 실행·승인·체크리스트·후속 작업·산출물을 담당한다. 같은 완료 상태를 두 곳에서 독립 관리하지 않는다.

문서 탭 둘은 ‘자료’로 합치되 **먼저 읽을 자료와 추천 이유**를 상단에 보존한다. 단순히 전체 문서 목록에 섞어 인수인계의 안내 기능을 잃지 않게 한다.

### 4.3 자료와 노트북

자료의 기본 보기는 원문이다. ‘만든 문서’는 별도 보기로 제공하며, 원문·업무 정리본·AI 초안·수정본·실제 확정 기록을 구별한다. 형식별로 내보낸 여러 파일은 하나의 산출물 아래에 판본별로 묶는다. 아직 내보내지 않은 초안도 찾을 수 있어야 한다.

노트북은 업무와 무관한 독립 조사도 지원한다. 업무에서 진입할 때는 ‘이 업무 자료로 묻기’와 선택 맥락을 전달한다. 자료가 여러 연도이면 대상 연도와 실제 포함된 연도 범위를 함께 표시한다. 출처 목록만으로 업무·수행 건·적용 연도가 충분히 설명된다고 가정하지 않는다.

기존 노트북을 여는 행위만으로 자료를 자동 추가하거나 선택을 변경하지 않는다. 명시적으로 연결된 기본 노트북을 재사용하고, 후보가 여럿이면 기존 노트북 선택 또는 새 작업 시작을 제공한다. 보관한 노트북은 자동으로 보관 해제하지 않는다.

## 5. 공통 데이터와 AI 처리 규칙

### 5.1 챙길 일 조회와 건수

읽기 전용 `AttentionSnapshot`에 해당하는 공통 조회를 만든다(이름은 구현 예시). 기존 반복 계산·제안·수행 건 조회를 조합하며 두 번째 제안 엔진을 만들지 않는다. 오늘·일정·업무는 같은 결과를 각 목적에 맞게 필터링한다.

항목에는 다음 정보를 둔다: 안정적인 항목 키, 유형, 업무/수행 건/실행/제안 ID, 대상 연도, 기한과 근거, 표시 이유, 우선순위, 이동 목적지. 같은 실행의 승인 대기를 ‘진행 중 수행 건’에서도 보여 줄 수 있지만 메뉴 배지에서 중복 합산하지 않는다.

오늘 메뉴의 숫자는 **조치가 필요한 고유 항목 수**로 정한다. 진행 중이라는 이유만으로 모든 수행 건을 더하지 않는다. 읽음과 조치 완료는 별개이고, 항목 유형별 개수는 화면에서 설명한다. 무시·만료·대체·미루기 상태는 기존 정책을 존중한다.

`new→seen`은 실제 보이는 카드에만 기록한다. 초기 구현에서 정확한 노출 판정이 어렵다면 카드 상세를 연 시점에 기록한다. 숨은 화면의 갱신, 5개 제한 밖의 카드, 스크롤 아래의 미노출 카드를 읽음으로 처리하지 않는다. 읽음 처리만으로 조치 건수가 감소하지 않게 한다.

조회와 상태 변경을 분리해 갱신 중 재귀 호출·카드 재정렬·스크롤 초기화를 방지한다. 새 제안 감지는 기존 감지 계층에서 수행하고 화면을 그릴 때 모델을 호출하지 않는다.

### 5.2 실행 수명과 종료

프로젝트의 `MainWindow`가 소유하는 실행 서비스를 두고 화면은 구독자로 바꾼다. 저장된 실행 ID를 기준으로 현재 상태를 읽는다. 기존 `catalog`가 계획과 실행 생성의 공통 시작점이며 기존 `Runner`가 승인을 강제한다.

| 사용자 행동 | 실행 정책 |
|---|---|
| 탭·메뉴 이동, 준비 작업 패널 닫기 | 실행 계속. 돌아오면 같은 실행 상태 표시 |
| 같은 실행을 다시 열기 | 기존 실행에 연결. 새 워커 생성 금지 |
| 다른 실행 시작, 이미 한 실행 수행 중 | 현재 실행과 이동 경로 표시. 1차에서는 자동 대기열·암묵적 순차 실행을 만들지 않음 |
| 중단 요청 | 협력적 중단을 요청하고 종료까지 상태 표시. 끝난 단계·파일 보존 |
| 승인 대기 | 자동 진행 금지. 해당 실행과 승인 내용을 확인한 뒤 진행 |
| 앱 종료·프로젝트 전환 | 중단 요청 후 스레드 종료 확인, 그 뒤 창·DB 정리. 기다리는 동안 진행 상태 표시 |
| 비정상 종료 후 재실행 | 기존 복구로 일부 완료 상태 정리, 사용자가 이어서 하기를 선택 |

작업 중인 스레드가 남아 있는데 제한 시간이 지났다는 이유로 객체·DB를 파괴하지 않는다. 워커는 자신의 DB 연결을 사용하고 UI 연결을 넘겨받지 않는다. 셸의 `shutdown()`과 프로젝트 전환 경로를 함께 수정한다.

메뉴 이동 중 중단과 앱 종료 중 중단을 같은 동작으로 구현하지 않는다. 재개 시 계획 버전·자료 판본·승인 유효성을 기존 실행기에서 재검증한다. 이번 범위의 ‘한 실행’은 행동 실행에 관한 정책이며 기존 자료 분석과 노트북 생성 작업의 동시성 정책을 무심코 바꾸지 않는다.

### 5.3 업무와 노트북 연결

화면 간 전달값은 `project`, `task_id`, 선택적 `case_id`, `target_year`, `notebook_id`, 선택 자료 ID·판본, 요청 목적이다. 이 중 자유 노트북에는 업무·수행 건이 없어도 된다. 날짜·연도는 자료 선택과 별개의 정보다.

`notebook_contexts`에 해당하는 명시적 연결을 추가하는 방향으로 설계한다. 업무·연도·수행 건과 노트북의 연결은 자료가 바뀌어도 임의로 바뀌지 않는다. 한 노트북이 여러 업무를 비교할 수 있으므로 다대다 관계를 허용하되 기본 진입 연결의 유일성을 정의한다. 구체 표 이름·제약은 구현 전 마이그레이션 설계에서 확정한다.

`linked_tasks()`는 기존 자료 구성 확인과 연결 후보 제안에만 사용한다. 기존 노트북에 업무 정리본이 있다는 이유만으로 특정 수행 건의 기본 노트북으로 자동 지정하지 않는다.

새 업무 노트북의 기본 자료는 업무 정리본과 검증 가능한 대표 원문으로 구성한다. 어떤 자료가 들어갔고 미분석·누락된 것이 무엇인지 표시한다. 자료 준비는 기존 수집 워커로 실행하고 완료 전 질문 가능 범위를 표시한다. 기존 대화의 자료 선택·허용 범위·판본 검사를 보존한다.

### 5.4 산출물 연결과 상태

실행 산출물과 노트북 산출물의 원장 표는 유지한다. 공통 조회는 `(작성 경로, 원본 ID, 판본)`으로 충돌 없이 식별하고 제목·업무·수행 건·연도·자료 스냅샷·파일 목록·상태를 반환한다.

노트북 산출물에는 생성 당시의 명시적 맥락을 별도 연결로 보존한다. 기존 산출물은 `업무 미연결`로 시작하거나 사용자가 연결하도록 한다. 노트북의 현재 자료 목록으로 과거 산출물의 업무·연도를 재계산하지 않는다. 업무 연결 변경은 기록하고 원래 생성 맥락과 근거를 덮어쓰지 않는다.

다음 축을 한 상태로 압축하지 않는다.

| 상태 축 | 예 | 금지할 오해 |
|---|---|---|
| 작성·편집 | AI 초안, 수정함 | 사람이 수정했으므로 검토·승인 완료라고 표시 |
| 기준 | 사전조사용, 공식 기준 반영 | 공식 기준 반영을 공식 발행·확정으로 표시 |
| 승인·확정 | 기록 없음, 승인 대기, 해당 작업 승인/확정 | 특정 체크리스트 등록 승인을 산출물 전체 승인으로 표시 |
| 근거 유효성 | 현재 유효, 변경됨, 원본 없음 | 최신 파일이라는 이유로 올해 기준에도 맞는다고 표시 |
| 출력 | 미출력, 내보낸 형식·판본 | 파일 내보내기를 업무 완료로 표시 |

확정본 표시는 실제 해당 확정 기록이 있을 때만 사용한다. 노트북에는 현재 없는 승인 기능을 조회 화면의 라벨만으로 만들어 내지 않는다. 근거 변경은 원자료 스냅샷과 인용 판본으로 검사한다.

### 5.5 AI의 역할과 근거

자유 문장을 임의 실행 계획으로 바꾸는 기능은 이번 개편에 포함하지 않는다. 현행 반복 업무 준비·자료 제출 요청 준비·회신 취합의 계획 틀을 유지하고 구체적인 버튼으로 시작한다. 현재 없는 실행 능력을 암시하는 ‘무엇이든 업무 요청’ 입력창을 만들지 않는다.

업무 정리본·AI 답변·초안은 파생 자료라는 출처 유형을 유지한다. 파생 자료를 검색 가능하게 제공하더라도 원문과 동등한 1차 근거로 취급하거나 업무 발견에 재투입하지 않는다. 사람의 검토와 지식 게시 절차를 보존한다.

### 7.2 사용자 검증

인수 직후 담당자·기존 담당자·AI에 익숙하지 않은 사용자를 포함하여 6~8명 내외의 형성적 시험을 제안한다. 실제 모집 결과를 적고, 소수 시험을 모집단 전체의 성공률로 일반화하지 않는다.

과제는 ① 오늘 조치할 일 찾기 ② 과거 패턴과 올해 기한 구분 ③ 다른 연도의 수행 건 열기 ④ 제안 수락 후 승인 내용 설명·초안 열기 ⑤ 업무 자료로 비교 질문 ⑥ 만든 결과 다시 찾기 ⑦ 새 프로젝트·노트북만으로 시작하기로 구성한다.

현재 화면과 새 화면에서 성공 여부·첫 선택·소요 시간·되돌아가기·도움 요청을 기록한다. 순서 효과를 줄이기 위해 과제·시안 순서를 나눈다. 무조건 80%·30초 같은 숫자를 통과 기준으로 삼지 않는다.

출시를 막는 결함은 잘못된 업무/연도 연결, 과거 기한의 현재 의무 오인, 승인 범위 오인, 결과 유실, 탐색만으로 실행 중단, 원문·범위 침범이다. 관찰된 중대한 오해는 수정하고 재확인한다. 순수 명칭 선호와 미적 선호는 차단 결함과 구분한다.

## 8. 이전·롤백·범위 관리

- UI 변경은 단계별 작은 변경 단위로 관리한다. 기존 작업 트리의 `main.py`, 테마, 서식 대화상자 등의 변경을 임의로 커밋·되돌리지 않는다. 변경이 겹치면 먼저 차이를 확인해 보존하는 방식으로 통합한다.
- UI만 바꾸는 P1과 연결 데이터를 추가하는 P2의 마이그레이션을 분리한다. 데이터가 생긴 뒤 UI를 되돌려도 연결·대화·산출물은 남겨 둔다. 구버전 실행 가능성은 별도 호환 검증 없이 보장하지 않는다.
- 삭제·합치기·보관된 업무/노트북의 링크 정책을 정한다. 대상이 없으면 다른 대상으로 자동 치환하지 않고 연결 불가 상태와 복구 경로를 제공한다.
- 자료 연결 해제와 원본 삭제, 산출물 메타데이터 삭제와 내보낸 파일 삭제를 구분하는 기존 정책을 유지한다.
- 새로운 상태 표시 모듈은 도메인별 상태를 공통 UI 문구로 변환한다. 실행 계층이 UI 테마나 위젯을 참조하도록 의존성을 뒤집지 않는다.

이번 개편 범위 밖: 자유 문장 자율 실행, 발송·결재·외부 시스템 입력, 프로젝트 통합 DB, 새 지식 승격 규칙, 의미 검증 모델 고도화, 모든 노트북의 AI 작업실 일괄 개명, 전체 테마 재작성.

## 9. 계획 완료의 정의

사용자가 **오늘에서 할 일을 발견하고 → 정확한 업무·수행 건으로 이동하고 → 근거를 확인하며 실행·질문·초안을 이어 가고 → 다른 화면을 다녀와도 진행과 결과를 다시 찾는 흐름**을 완성하는 것이 목표다.

최종 산출물은 메뉴 변경 코드만이 아니라 공통 조회·실행 수명 관리·명시적 맥락 연결·산출물 탐색·마이그레이션·검증 기록·현행 설명서를 포함한다. A의 실행 중심 구조와 B의 근거·맥락 설계를 결합하되, 추정 연결·불명확한 건수·숨은 중단을 제거하는 것을 우선한다.
